# AdvisKV 项目速读：从演示到源码

> 面向推荐架构及分布式基础设施面试。按“先跑通，再讲链路，再解释取舍”阅读。能力、结果与限制的证据见[证据与边界](证据与边界.md)；练习题见[分层面试题库](分层面试题库.md)。

按图复习可从[面试图解目录](图解/README.md)开始：先用 [7 张组件架构图](图解/00-组件架构.md)看清模块与通信，再用 19 张 Mermaid 流程图串起题库。

## 1. 30 秒介绍

AdvisKV 是一个 C++17 分布式 Key-Value 系统，客户端用 `db + table + key` 访问数据。Catalog 保存库表元数据并推进 DDL，Topo 管理节点、分片副本和路由，Storage 用 Raft 复制写入，以 WAL 与 Snapshot 支持重启和落后副本恢复；SDK 缓存路由，向 Leader 发请求，并处理路由变化、重试及写结果不确定性。项目支持本地多进程演示，当前版本的主要限制是内存 Map 引擎、固定分片数以及单进程 Catalog/Topo。[实现入口：`src/catalog/service/ddl_service.cpp`、`src/topo/service/route_service.cpp`、`src/storage/replica/replica.cpp`、`src/sdk/client.cpp`；限制：`README.md`]

面试时把它定位为**分布式基础设施项目**。推荐架构相关的是分片、在线副本调整、读写一致性、故障恢复和延迟/吞吐量权衡。AI/Agent 相关的是有状态服务的可靠性经验；当前代码没有向量索引、模型调用或 Agent 框架接入。

## 2. 从零运行

推荐 Linux，准备 C++17 编译器、CMake 3.20+、Ninja 或 Make、Git、Python 3。首次运行：

```bash
git submodule update --init --recursive
./scripts/setup.sh
python3 scripts/verify_project.py
```

`verify_project.py` 调用现有构建脚本，拉起 1 Catalog、1 Topo、3 Storage，检查三副本建表、Put/Get、覆盖、删除、删表重建的关键输出，并在正常结束、报错或中断时停止这次启动的服务。它会清空当前 `BUILD_DIR/e2e_test` 下的本地测试数据；默认 `BUILD_DIR=build`；若本机没有 Ninja 且已有 `build/` 是 Ninja 缓存，验证入口自动使用 `build-make/`。缺少依赖时先执行上面的 `setup.sh`。代码入口：[验证脚本](../../scripts/verify_project.py)、[集群夹具](../../test/e2e/cluster.py)、[基础 E2E 用例](../../test/e2e/test_basic_chain.py)。

交互式演示：

```bash
./scripts/adviskvctl_demo.sh
```

```text
create_db demo_db dc1
create_table demo_db demo_table 1 1 default
wait_table demo_db demo_table
put demo_db demo_table k1 v1
get demo_db demo_table k1
route demo_db demo_table k1
quit
```

交互式脚本默认使用 `build/bin`；若验证入口选择了 `build-make/`，用 `BUILD_DIR=build-make ./scripts/adviskvctl_demo.sh`。否则先运行验证入口或 `./scripts/build.sh`。演示会清空 `build/demo` 并操作默认端口的本地进程；不要在另一个正在使用这些端口的集群旁启动。[演示脚本](../../scripts/adviskvctl_demo.sh)、[CLI 命令](../../tools/cli/src/adviskvctl.cpp)。如需跑某个 E2E 用例，可执行 `./scripts/e2e_pytest.sh test/e2e/test_basic_chain.py::test_catalog_to_storage_basic_kv_chain -q`；不传路径时运行整个 E2E 目录。

## 3. 一张模块图

```text
adviskvctl / 应用
       │ DDL                     │ KV
       ▼                         ▼
    Catalog                     SDK ──────► Topo 路由
       │ Place/Alter/Drop         │              ▲
       ▼                          └─────► Storage Leader
     Topo ◄──── 节点心跳/副本状态 ─────── Storage 副本
       │                                 │
       └── 期望副本、路由 ────────────────┤ Raft 复制
                                         └ WAL / Snapshot / Map
```

- **Catalog**：处理库表 DDL，持久化表状态；建表先写 Catalog，再向 Topo 下发期望状态，由后台 reconciler 收敛。看 `src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp`、`src/catalog/store/catalog_store.cpp`。
- **Topo**：根据节点心跳和表规格维护副本组，发布可写路由；表就绪需要满足副本和路由条件。看 `src/topo/service/table_service.cpp`、`src/topo/reconcile/replica_group_plan_reconciler.cpp`、`src/topo/reconcile/replica_group_membership_reconciler.cpp`、`src/topo/service/route_service.cpp`。
- **Storage**：Replica 封装 Raft Core、持久化、状态机和读校验；NodeAgent 与 Topo 通信。看 `src/storage/replica/replica.cpp`、`src/storage/node_agent/node_agent.cpp`、`src/storage/persist/persist_engine.cpp`。
- **SDK**：定期更新并原子发布路由快照，用稳定哈希计算 shard，按错误类型重试与刷新路由。看 `src/sdk/route_cache.cpp`、`src/sdk/client.cpp`、`src/common/stable_hash.h`。

## 4. 核心链路

### 建表和在线改副本

1. CLI/Catalog 收到建表请求，Catalog 创建表记录；Topo 暂时不可达时表仍保留在 `ADDING` 状态，后台再提交。[ `src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp` ]
2. Topo 保存表的目标规格，对每个 shard 建立期望副本组，并通过节点选择器选择健康节点。[ `src/topo/service/table_service.cpp`、`src/topo/reconcile/replica_group_plan_reconciler.cpp`、`src/topo/selector/node_selector/node_selector.cpp` ]
3. Storage 的 NodeAgent 注册、心跳并执行副本创建/删除；成员变更经 Raft 协调，路由服务只发布满足 Leader 条件的路由。[ `src/storage/node_agent/node_agent.cpp`、`src/topo/reconcile/replica_group_membership_reconciler.cpp`、`src/topo/service/route_service.cpp` ]
4. 改副本数是“更新目标规格 → 反复收敛”的异步过程；要分别看期望数、实际成员、路由和表状态，不能把 DDL RPC 返回 OK 等同于全部副本已就绪。[ `src/catalog/service/ddl_service.cpp`、`src/topo/service/table_service.cpp`、`test/e2e/test_basic_chain.py` ]

### Put：从 SDK 到提交

```text
KVClient::put
  → RouteCache: table_id + stable_hash(key) % shard_count
  → StorageClient::put(leader)
  → StorageServiceImpl::Put
  → Replica::put / ReplicaLoop
  → Raft Core 提议 → PersistEngine(WAL) → Raft 复制
  → 多数派提交 → Put 返回 OK
                                  ↘ 后台 ReplicaApplier → KvStateMachine(Map)
```

当前实现的 Put 等待 Raft 提案提交后返回 OK，状态机 apply 可在本次返回后由后台任务完成；Get 会先将状态机追到安全读位置。SDK 对可重试错误区分是否刷新路由；同一逻辑写沿用 `request_id`。若 RPC 超时或仍未确认提交，最终可能返回 `UNKNOWN`，业务应持相同 `request_id` 重试，不能把未知当成明确失败。状态机将 request record 纳入 Snapshot，便于恢复后去重。[ `src/sdk/client.cpp`、`src/sdk/storage_client.cpp`、`src/storage/handler/storage_service_impl.cpp`、`src/storage/replica/replica.cpp`、`src/storage/replica/replica_loop.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`；用例 `test/storage/replica/replica_test.cpp` ]

### Get：为什么要 ReadIndex

SDK 仍先解析路由并请求 Leader。Storage 在读取 Map 前确认当前任期已有已提交日志，向多数派确认 Leader 身份，取得 read index，并将状态机推进到该索引；多数派不可达时不会假装读是线性一致的。[ `src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/replica/replica.cpp`；用例 `test/storage/raft/core/raft_cluster_test.cpp` ]

### 重启、日志追赶与 Snapshot

写入的日志由 PersistEngine 写 WAL；状态机当前使用 Map，Snapshot 包括 KV、request record 和应用位置。重启时先恢复 Snapshot，再处理后续 WAL；若落后副本缺少所需日志，走 Snapshot 安装再追赶。这里的“内存引擎”不等于“完全不落盘”，也不等于已经具备生产级磁盘 KV 引擎。[ `src/storage/persist/persist_engine.cpp`、`src/storage/replica/replica.cpp`、`src/storage/replica/replica_snapshot_coordinator.cpp`；用例 `test/storage/persist/persist_engine_test.cpp`、`test/e2e/test_basic_chain.py` ]

## 6. 推荐架构及 AI/Agent 的迁移表达

推荐架构面试可讨论：用户特征/候选集等有状态数据如何按 key 分片；单 shard 热点、扩容和再均衡如何影响延迟；强一致与吞吐量如何取舍；故障切主期间写结果如何向上层暴露。这些是基于本项目的**设计延伸**，并非现有推荐业务实现。

AI/Agent 面试可讨论：会话状态、任务进度、工具调用结果如果要持久化，需要什么幂等键、超时重试和恢复语义；如何避免“请求超时但工具已执行”的重复副作用。AdvisKV 的 `request_id` 与 `UNKNOWN` 语义可作为类比；现有项目没有 Agent 状态存储适配器或模型服务。[ `src/sdk/client.cpp`、`README.md` ]
