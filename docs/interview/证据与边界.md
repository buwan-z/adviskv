# AdvisKV：能讲什么、证据在哪里、边界是什么

> 本文帮助你把“代码有实现”“测试通过”“历史报告有数据”“尚未实现”分开。项目主线见[项目速读](项目速读.md)，追问练习见[分层面试题库](分层面试题库.md)。候选贡献故事应按你真实完成的部分使用；仓库和测试能证明功能，不能单独证明个人贡献比例。

## 1. 证据分级

| 等级 | 含义 | 可以怎么说 |
| --- | --- | --- |
| A：本机刚验证 | 在当前环境执行并看到了成功结果 | “当前环境跑通了三副本基础 KV E2E” |
| B：有自动化用例 | 仓库有对应单元或 E2E 用例；未必在本次全部重跑 | “项目有覆盖该场景的测试” |
| C：代码可定位 | 能指到实现，但本次没有独立验收 | “代码实现了该流程，仍需按场景复测” |
| D：历史报告 | 仓库保留当时环境、参数及结果 | “历史本地报告记录了……” |
| E：设计延伸 | 面试时的推演，不属于当前功能 | “如果用于推荐/Agent 场景，我会……” |

当前环境记录（2026-10-01）：`ctest --test-dir build-make` 中抽取的 4 项通过：MapEngine Put/Get、三节点 Leader 选举、Catalog 建库建表、Topo 建表收敛；最小 Python E2E 通过；新增 `python3 scripts/verify_project.py` 通过（本机缺少 Ninja，自动选用 `build-make` / Unix Makefiles），检查了创建库表、三副本就绪、16 个键 Put/Get、覆盖、删除及删表重建，并完成服务清理。这里不是“256 项测试全部通过”或“全部故障场景已在本机重跑”。[验证入口](../../scripts/verify_project.py)、[基础用例](../../test/e2e/test_basic_chain.py)

## 3. 性能数字怎么讲

仓库 v0.1.0 历史报告来自 Apple M3 Pro、macOS 15.7.4、36 GiB 内存、单机多进程（1 Catalog + 1 Topo + 5 Storage），客户端到服务均为本机通信。默认负载：16 线程、2 shards、3 replicas、128 字节 value、30,000 请求。报告记录：Put 约 9,800 success QPS，Get 约 11,059 success QPS，80% 读混合负载约 8,230 success QPS；对应 p99 约 5,623/2,211/4,474 微秒。[报告索引](../v0.1.0/benchmark/README.md)、[原始 CSV](../v0.1.0/benchmark/benchmark_results/)

可说“这说明在该固定单机环境和参数下的端到端表现”。不能外推为跨机吞吐、生产容量、线性扩展或任意键分布下的性能。本次没有重新执行 benchmark。面试官问瓶颈时，先分 SDK 路由/RPC、Leader 排队、Raft 多数派确认、WAL fsync、状态机 apply 和读校验，再用分层 metrics 和火焰图验证，别仅凭 QPS 表猜结论。

SDK 重试历史验收也应带条件：固定压力下 `max_retries=0` 的 5000 次 Put 有 2536 次最终失败/UNKNOWN；`max_retries=1` 有 56 次。故障切主实验中提高重试次数后，仍存在失败/UNKNOWN，不能表述为“故障切换无损、业务零失败”。[重试验收](../v0.1.0/retry.md)

## 4. 七个可追问的贡献故事

以下是口述骨架，使用前把“我做了”的环节与你实际提交或设计记录核对。结果只引用相应测试或历史报告。

### 故事 1：SDK 在路由变化时完成写请求

- **背景**：Leader 切换或缓存路由过期时，直接请求旧 Leader 会失败。
- **方案**：按错误码决定是否重试与刷新整表路由，在总超时预算内退避；写操作复用同一 `request_id`。
- **取舍**：额外 RPC 和延迟换取更高的成功概率；路由刷新和 Storage 尝试分别限额。
- **问题**：RPC 失败时服务器可能已提交，不能简单返回“失败”。
- **结果**：代码在不确定写最终返回 `UNKNOWN`；历史固定压力验收记录了重试前后的失败/UNKNOWN 比例。
- **证据/追问**：`src/sdk/client.cpp`、`docs/v0.1.0/retry.md`。解释同一 `request_id` 为什么必须贯穿重试，以及客户端超时后为何不能自动生成新 ID。

### 故事 2：用 PreVote 降低旧 Leader 恢复的干扰

- **背景**：被隔离的节点重新连通时，若直接增加任期发起选举，可能扰动健康多数派。
- **方案**：真实选举前先征询投票意愿，检查日志新旧与近期 Leader 活跃状态。
- **取舍**：多一轮选举消息，换取隔离恢复时更稳定的 Leader。
- **问题**：旧节点、少数派、当前任期响应和日志新旧的组合容易漏判。
- **结果**：仓库有旧 Leader 回归、分区 follower 等 Raft Cluster 用例；本机本次只抽验了三节点选主。
- **证据/追问**：`src/storage/raft/core/raft_core_election.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。解释 PreVote 是否改变本地 term。

### 故事 3：WAL、Snapshot 与重启恢复

- **背景**：内存 Map 服务重启后需要恢复 KV、Raft 状态和去重记录；WAL 尾部可能因崩溃不完整。
- **方案**：写日志和 Snapshot 到磁盘，恢复时加载快照与后续 WAL；检查损坏尾部并进入必要的追赶状态。
- **取舍**：fsync/快照增加写入与磁盘成本，换来可恢复性；Map 仍需加载整份状态到内存。
- **问题**：区分未提交尾部与已提交损坏；快照边界和日志索引必须连续。
- **结果**：有部分写、CRC 损坏、重启等测试；基础演示本次未独立验证掉电语义。
- **证据/追问**：`src/storage/persist/persist_engine.cpp`、`test/storage/persist/wal_crash_injection_test.cpp`。问到“绝对不丢数据”时限定故障模型、fsync 和多数派条件。

### 故事 4：ReadIndex 保障 Leader 读

- **背景**：旧 Leader 在网络分区后仍可能自认为 Leader；新 Leader 刚当选时旧任期日志也可能尚未安全应用。
- **方案**：当前任期先有已提交 entry，再通过多数派确认身份，读前 apply 至 read index。
- **取舍**：读延迟和可用性受多数派 RPC 影响；换取项目中的线性一致读语义。
- **问题**：不能只看本地 `is_leader` 或本地 Map。
- **结果**：Raft Cluster 有 ReadIndex 用例；代码在多数派确认失败时返回错误。
- **证据/追问**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/replica/replica.cpp`。

### 故事 5：期望状态驱动在线副本调整

- **背景**：一次 RPC 不能保证多个节点的成员变更立即完成；节点可能失败或重启。
- **方案**：Catalog 保存 DDL 状态，Topo 保存期望副本数，由后台 reconcile 持续推进；先 learner 追赶，再升 voter/移除旧成员。
- **取舍**：异步最终收敛，表状态和路由需要分开观测；优于把长流程塞进一个同步 RPC。
- **问题**：坏副本替换、缩容到零、并发写与配置变更的交错。
- **结果**：仓库有 resize、scale-to-zero、故障期间调整的 E2E 用例；这些用例并未在本次全部运行。
- **证据/追问**：`src/topo/reconcile/`、`src/topo/service/table_service.cpp`、`test/e2e/test_basic_chain.py`。

### 故事 6：控制面崩溃后的收敛

- **背景**：Catalog 向 Topo 下发建表后可能崩溃，无法依赖“一次调用完成”。
- **方案**：先持久化表状态，再通过状态查询和后台 reconciler 重试、确认。
- **取舍**：需要处理重复提交和中间态；换取进程重启后的可继续性。
- **问题**：崩溃发生在持久化前后，会看到不同状态。
- **结果**：仓库有 create-table crash、Catalog/Topo 恢复 E2E 用例；单进程控制面仍是限制。
- **证据/追问**：`src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp`、`test/e2e/test_basic_chain.py`。

### 故事 7：从功能测试到端到端性能证据

- **背景**：单元测试不能证明 Catalog→Topo→Storage 链路可运行，单个 QPS 数字也不能说明故障表现。
- **方案**：用 GoogleTest 验证模块状态机与边界，用 Python E2E 拉多进程集群，用 benchmark/failover 工具记录参数和结果。
- **取舍**：E2E 慢且可能受环境影响，因此保留最小 smoke 流程和分层测试。
- **问题**：隔离测试数据、端口、进程清理与历史结果口径。
- **结果**：本机通过最小 E2E 和新验证入口；历史性能与故障数据作为独立证据。
- **证据/追问**：`scripts/verify_project.py`、`test/e2e/cluster.py`、`docs/v0.1.0/benchmark/`。

## 5. 必须主动说明的限制

- KV 运行时引擎是内存 Map；WAL/Snapshot 提供恢复，但没有成熟磁盘 KV 引擎。[ `src/storage/engine/map_engine.cpp`、`README.md` ]
- `request_id` 记录暂无 TTL，长期运行会带来记录增长问题。[ `src/storage/raft/state_machine/kv_state_machine.cpp`、`README.md` ]
- shard 数建表时固定，尚无在线 split 或动态 rebalance。[ `src/sdk/route_cache.cpp`、`README.md` ]
- Catalog 和 Topo 各为单进程，控制面尚未高可用。[ `README.md` ]
- 坏副本替换后旧副本恢复的选择策略仍有优化空间。[ `docs/版本.md` ]

这些限制适合用“如果重做，我会先测量/定义语义，再设计改造”的方式回答，不要把规划当成已交付功能。
