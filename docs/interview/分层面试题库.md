# RaftBox 分层面试题库与评分标准

> 先读[项目速读](项目速读.md)和[证据与边界](证据与边界.md)。题库按项目主线、基础原理、故障排查、岗位设计题组织。每题的“合格”是至少应说出的事实，“加分”是能经受追问的因果与取舍，“失分”列出常见错误。代码入口用于复盘，不代表该场景在本次全部复测。标有“设计推演”的题目不属于当前已实现功能。

## 使用方法与统一评分

每题 0–4 分：**0** 没有回答或核心结论相反；**1** 只说术语，不能讲流程；**2** 说清“合格”要点；**3** 再说清“加分”中的一个边界、取舍或故障；**4** 能结合代码/测试定位并解释追问。含错误保证（例如把 `UNKNOWN` 说成一定没写入）时最高 1 分。系统设计题的 4 分还要有量化目标、演进和验证方案。先独立回答 90 秒，再看标准；项目题应能打开对应源码给面试官解释。

## A. 先讲清项目（1–8）

### 1. 怎么用 30 秒介绍 RaftBox？

**合格**：C++17 分布式 KV；Catalog 管 DDL、Topo 管副本和路由、Storage 用 Raft/WAL/Snapshot，SDK 路由请求。**加分**：给出三副本本地 E2E 证据与单进程控制面、固定 shard 等边界。**追问**：一次 Put 经过哪些模块？**失分**：声称生产部署或 AI 功能已完成。**依据**：`README.md`、`scripts/verify_project.py`。

**口述回答**：“RaftBox 是我参与实现的 C++17 分布式 KV 项目。Catalog 管理库表，Topo 负责副本放置和路由，Storage 用 Raft 复制写入，并通过 WAL 和 Snapshot 做持久化恢复，SDK 根据路由访问对应 shard。项目有三副本基础链路和恢复相关测试；目前 KV 引擎仍是内存 Map，控制面也还没有高可用。”请按自己的实际贡献调整“我参与实现”。

### 2. 为什么把 Catalog、Topo、Storage 拆成三个模块？

**合格**：分别承担库表元数据/DDL、期望副本与路由、实际数据复制。**加分**：说明控制面异步收敛和数据面高频读写的节奏不同；Catalog/Topo 当前单进程是可用性短板。**追问**：Topo 故障时已有路由能否继续访问？需按 SDK 缓存和路由过期条件回答。**失分**：说三个模块都通过 Raft 高可用。**依据**：`src/catalog/`、`src/topo/`、`src/storage/`。

**口述回答**：“拆成三个模块是因为它们管理的状态和工作节奏不同：Catalog 管库表元数据和 DDL，Topo 管副本期望状态与路由，Storage 承担实际读写和 Raft 复制。这样 DDL 可以异步推动副本收敛，而高频读写留在 Storage 数据路径上。当前 Catalog 和 Topo 仍是单进程，这是控制面可用性上的限制。”

### 3. 建表请求返回成功，什么时候表才真正可用？

**合格**：Catalog 持久化 ADDING，Topo 建目标副本，Storage 执行创建，表与可写路由满足条件后进入就绪。**加分**：区分 DDL RPC 的 OK 与最终 NORMAL；Topo 不可达可由 reconciler 后续重试。**追问**：启动时没有足够健康节点怎么办？**失分**：把“请求返回 OK”当“已可读写”。**依据**：`src/catalog/service/ddl_service.cpp`、`src/topo/service/table_service.cpp`。

**口述回答**：“建表 RPC 返回 OK，通常只说明请求被接受，不一定代表表已经能读写。Catalog 会先记录创建中的状态，Topo 再安排副本，Storage 创建副本并形成可用路由；达到就绪条件后表才算可用。如果中间步骤暂时失败，后台 reconciler 可以继续检查并重试。”

### 4. 一个 Put 请求从客户端到写入完成经历什么？

**合格**：SDK 查路由 → Leader RPC → Replica 提议 Raft 日志并持久化 → 多数派提交后 Put 可返回 OK；已提交日志随后由后台任务 apply 到状态机。**加分**：说明在路径中超时可能产生未知结果，同一逻辑请求沿用 `request_id`；Get 读前会追到安全的 apply 位置。**追问**：本地日志写入后但未多数派确认能否回 OK？**失分**：将 WAL 写入等同多数派提交，或说当前 Put 必须等本次 apply 才能回 OK。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`、`src/storage/replica/replica_applier.cpp`。

**口述回答**：“Put 时，SDK 先根据 Key 找到 shard，再向路由中的 Leader 发请求。Leader 把操作作为 Raft 日志提议，日志先持久化，再复制给副本；达到多数派提交条件后，这次 Put 可以返回 OK。后台任务随后把已提交日志 apply 到状态机。若超时，客户端可能不知道写入到底有没有提交，所以同一逻辑请求重试要复用 `request_id`。”

### 5. Get 为什么不能直接从 Map 里读？

**合格**：确认自己仍是 Leader、取得 read index、apply 至该位置再读取。**加分**：解释新 Leader 当前任期 no-op 提交和多数派确认，指出多数派不可达时读可能失败。**追问**：如果允许陈旧读如何设计独立 API？**失分**：只看 `is_leader` 就声称线性一致。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

**口述回答**：“Get 虽然最后是从内存 Map 取值，但为了线性一致，不能只看本地的 Leader 标记。副本会先通过 ReadIndex 确认自己仍被多数派认可为 Leader，再把状态机推进到安全读位置，之后才读 Map。多数派确认失败或 apply 没追上时，就返回错误而不是冒险返回旧值。”

### 6. 你能拿出哪些证据说明项目做成了？

**合格**：最小三副本 E2E 本机通过；仓库有单测、故障 E2E、benchmark 报告。**加分**：区分本次抽验与未重跑的测试，讲出可重复命令。**追问**：历史数字的机器和工作负载？**失分**：说 256 项本机全通过，或将历史 benchmark 说成今天新测。**依据**：`scripts/verify_project.py`、`docs/v0.1.0/benchmark/`。

**口述回答**：“我会把证据分开讲：基础三副本链路有自动化验收入口，仓库也有 Raft、WAL、恢复和故障场景的测试；Benchmark 报告记录了当时机器、拓扑和负载参数。哪些测试是我本机刚跑过、哪些只是仓库有用例、哪些是历史数据，我会分别说明，不把历史成绩说成刚测结果，也不把仓库所有功能都说成个人完成。”

### 7. 项目现在最大的不足是什么？

**合格**：内存 Map（容量受内存限制，恢复数据量大时较慢）；shard 数建表时固定（不能 split/rebalance）；Catalog/Topo 单进程（控制面无故障接管）；`request_id` 无 TTL（去重记录持续增长）。**加分**：按业务瓶颈排序：数据容量与恢复、热点扩容、控制面可用性、去重记录增长。**追问**：先改哪个、如何验收？例如接入磁盘 KV 引擎，测大数据集下的读写、重启恢复时间和峰值内存。**失分**：只说“还要优化性能”；认为 Snapshot 会降低 Map 内存占用，或增加副本数等于 shard 扩容。**依据**：`README.md`“当前限制”、`docs/版本.md`“后续”。

**口述回答**：“当前最明显的限制之一是 KV 状态存在内存 Map 里，数据量受内存限制，重启时也要恢复回内存。另外 shard 数建表后固定，Catalog 和 Topo 还是单进程，request_id 去重记录也没有 TTL。优先改哪项要看目标；如果要扩大数据容量，我会先评估磁盘 KV 引擎，并用大数据集恢复时间、峰值内存和性能做验收。”

### 8. 面试官问你具体做了哪些工作，怎么回答？

**合格**：按个人真实工作选一条链路，讲背景、方案、取舍、问题、结果，并打开对应代码/测试。**可选讲法**：SDK 重试——路由错误时刷新路由；不确定写复用 `request_id` 重试，预算耗尽返回 `UNKNOWN`。Get——路由到 Leader，经 ReadIndex 多数派确认并 apply 到安全位置后读 Map。**加分**：明确个人与团队边界、哪些结果是历史报告。**追问**：最难的 bug 如何复现？**失分**：把整个仓库每项功能都说成个人独立完成，却无法解释。**依据**：[七个故事](证据与边界.md)、`src/sdk/client.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

**回答示例（按自己的实际贡献修改）**：

- **SDK 重试**：“我负责/参与/分析 SDK 的 Put 重试。SDK 先从路由缓存找 shard 的 Leader；遇到 `NOT_LEADER` 或 `RPC_ERROR` 等错误时会刷新路由并重试，遇到 `NOT_YET_COMMIT` 则可在预算内重试但不刷新路由。每次重试沿用同一个 `request_id`，并受总超时和重试次数限制；仍无法确认结果时返回 `UNKNOWN`，因为请求可能已经提交。可沿 `KVClient::put()` → `run_kv_request()` → `execute_with_retry()` 查看，再看状态机如何记录 request ID。”
- **Get 链路**：“我负责/参与/分析 Get 的线性一致读。SDK 按 key 算 shard，从路由中选 Leader；Storage 的 `Replica::get()` 不只检查本地 Leader 标记，而是调用 ReadIndex 检查当前任期提交状态，并向副本确认多数派仍认可自己。确认后取得 `read_index`，apply 已提交日志直到 `apply_index >= read_index`，再调用状态机的 `get()` 读 Map。多数派不可达或 ReadIndex 未就绪时返回错误，不冒险返回旧值。可沿 `KVClient::get()` → `Replica::get()` → `ReplicaReadIndexChecker` → `RaftCore::build_append_entries_for_read()` 查看。”

## B. C++、并发与工程基础（9–18）

### 9. 更新路由缓存时，怎样避免读线程看到不完整数据？

**合格**：建好新的不可变 `TableRouteSnapshot` 后，用 `shared_ptr` 原子发布；读线程通过原子 load 取得完整快照。**加分**：不会读到半更新路由，但快照仍可能过期，遇到 `NOT_LEADER` 等错误需刷新。**追问**：原子操作和引用计数的成本？**失分**：认为线程安全就代表路由最新。**依据**：`src/sdk/route_cache.cpp`。

### 10. Replica 为什么要用多把锁和任务队列？

**合格**：需要多把锁，因为 Raft Core、KV 状态机和 Snapshot/持久化是不同的共享状态，需分别保护；需要任务队列，因为 RPC、心跳和复制响应可能并发到达，Raft 状态变化要排队串行处理，写提案还可合批。**加分**：apply、RPC 等仍可并发；注意锁顺序，避免持锁等待网络。**追问**：如何排查死锁？**失分**：认为整个 Storage 是单线程，或“用了 mutex 就没有并发问题”。**依据**：`src/storage/replica/replica.h`、`src/storage/replica/replica_loop.cpp`、`src/common/serial_task_runner.cpp`。

### 11. 什么时候用 `atomic`，什么时候用 `mutex`？

**合格**：单个独立值（如计数器）用 `atomic`；多个字段需一起保持一致时用 `mutex`。**加分**：SDK 的 request ID 序号用 `fetch_add(relaxed)`；路由快照完整构造后原子发布；Raft Core 多字段由 mutex 保护。`relaxed` 保证计数原子递增，但不用于同步其他数据。**追问**：为什么不能把所有字段都改成 atomic？**失分**：认为 atomic 自动保证多个字段的一致性。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/storage/replica/replica_loop.cpp`。

### 12. 异步任务里的 C++ 对象生命周期有什么风险？

**合格**：后台任务/回调若持有对象指针，对象过早销毁会导致悬空访问；析构前要停止任务并等待线程退出（`stop`/`join`）。**加分**：`RouteCache` 析构时停止刷新任务；Replica 先停 apply 和消息线程，再停 loop。`shared_ptr` 不会自动取消任务或保证关闭顺序。**追问**：怎样避免回调访问已销毁对象？**失分**：认为用了 `shared_ptr` 就无需管理异步任务。**依据**：`src/sdk/route_cache.cpp`、`src/common/background_task.cpp`、`src/storage/replica/replica.cpp`。

### 13. 怎样稳定复现 Raft 并发问题？

**合格**：固定节点和初始 Leader，控制分区及消息顺序；记录 term、日志/commit index、成员角色和消息时序。**加分**：模拟集群适合复现 Raft 状态问题；真实线程竞态用并发测试和 TSan 检查，ASan 补查内存错误。**追问**：如何稳定复现旧 Leader 收到延迟消息？**失分**：只靠随机 sleep 或把逐步 tick 的协议测试说成并发测试。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`scripts/asan/`。

### 14. `request_id` 如何生成，怎样处理 ID 冲突？

**合格**：默认 `request_id` 由进程随机实例值和原子递增序号组成；同一次 SDK 写调用的重试复用该 ID。**加分**：跨重启重试需由调用方保存并传回原 ID；Storage 对相同 ID 去重，并拒绝内容不同的复用。随机 ID 的碰撞概率低但非零。**追问**：跨地域业务 ID 如何设计？**失分**：重试时生成新 ID。**依据**：`src/sdk/client.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/replica/replica_loop.cpp`。

### 15. 为什么要区分单次 RPC 超时和整个请求超时？

**合格**：单次 RPC timeout 限制一次网络调用；总 timeout 限制完整 Put/Get（含路由刷新、重试和退避）。每次调用按 `min(剩余总预算, 单次 RPC 上限)` 设置 deadline。**加分**：同时限制重试次数；例如默认单次 RPC 1 秒、总请求 3 秒。**追问**：每次重试如何计算剩余时间？**失分**：每次重试都重新获得完整总超时。**依据**：`src/sdk/client.cpp`、`src/sdk/config.h`。

### 16. RAII 怎样帮忙处理资源清理？

**合格**：RAII 将清理绑定到对象析构，函数提前返回也会执行；项目 `Defer` 用于记录请求结果、关闭文件描述符。**加分**：引用捕获的变量必须活得比 guard 久，清理函数不应抛异常。**追问**：`Defer([&])` 何时安全？**失分**：把 RAII 仅理解为智能指针。**依据**：`src/common/defer.h`、`src/sdk/client.cpp`、`src/storage/persist/persist_engine.cpp`。

### 17. 如何确保不同进程把同一个 Key 算到同一 shard？

**合格**：SDK 与 Topo 共用固定的 FNV-1a 64 位哈希，按 `hash(key) % shard_count` 算 shard。**加分**：改变 shard 数或哈希算法会重映射 key，需迁移数据；当前 shard 数建表时固定。**追问**：如何设计 split 迁移？**失分**：用不保证跨版本稳定的 `std::hash` 做持久路由，或直接改 shard 数。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`、`src/topo/service/route_service.cpp`。

### 18. 怎样在另一台机器上复现编译和运行环境？

**合格**：`git submodule update --init --recursive` 获取 vcpkg，运行 `scripts/setup.sh` 安装依赖，`scripts/build.sh` 构建，再分别运行 C++ 测试和 `scripts/e2e_pytest.sh`。**加分**：同一 build 目录的 CMake generator 必须一致；可按依赖、配置/编译、测试运行阶段定位 CI 失败。**追问**：如何切换 Ninja 和 Makefiles？**失分**：在已有 build tree 中混用 generator，或只给本机绝对路径。**依据**：`CMakeLists.txt`、`scripts/setup.sh`、`scripts/build.sh`、`scripts/run_test.sh`、`scripts/e2e_pytest.sh`。

## C. RPC、SDK 与结果语义（19–28）

### 19. 客户端刚启动、路由缓存还没有数据时怎么办？

**合格**：冷启动缓存 miss 时，SDK 向 Topo 拉整表路由，缓存后按 key 算 shard 并选 Leader；拉取失败则返回错误，不盲发 Storage。**加分**：后台定期刷新与路由错误后的请求路径刷新并存；缓存命中时不必每次访问 Topo，但可能过期。**追问**：Topo 暂时不可用而缓存已有路由时怎么办？**失分**：认为每次请求都必须访问 Topo，或缓存永远最新。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/sdk/topo_route_client.cpp`。

### 20. 遇到哪些错误时 SDK 会刷新路由？

**合格**：可重试错误分两类：路由可能失效（`NOT_LEADER`、`REPLICA_NOT_FOUND`、`ROUTE_NOT_FOUND`、`IS_RECOVERING`、`RPC_ERROR`）则刷新路由；暂时未就绪（`NOT_YET_COMMIT`、`READ_INDEX_NOT_READY`、`RESOURCE_EXHAUSTED`）则沿原路由重试。**加分**：Storage 最多尝试 `max_retries + 1` 次，路由刷新次数受 `route_max_retries` 限制；路由查询、RPC 和退避共用总 deadline，每次 RPC 取单次上限与剩余时间的较小值。写重试复用同一 `request_id`。**追问**：为什么重试次数和总超时都要限制？**失分**：所有错误都刷新路由或无限重试。**依据**：`src/sdk/client.cpp`、`src/sdk/config.h`。

### 21. 写请求超时后返回 `UNKNOWN` 表示什么？

**合格**：`UNKNOWN` 表示客户端在重试预算内无法确认写入是否提交；请求可能未到 Leader，也可能已提交但响应丢失。**加分**：用相同 `request_id` 和内容重试；单独 Get 只反映当前值，不能总证明原请求是否提交。**追问**：之后发生覆盖写，Get 为什么无法确认原请求？**失分**：把 `UNKNOWN` 当成确定失败。**依据**：`src/sdk/client.cpp` 中 `finalize_status`、`execute_with_retry`。

### 22. 怎样让写请求重试时不重复生效？

**合格**：SDK 为每笔逻辑写入生成 `request_id`，重试时复用。Storage 先查已应用记录，再查 inflight 提案：同 ID、同内容则去重或等待；同 ID、不同内容则报错；都没有才提交新 Raft 提案。**加分**：请求记录保存在状态机并纳入 Snapshot，重启后仍可去重；当前无 TTL，长期运行会持续增长。**追问**：客户端重启后怎样复用原 ID？**失分**：重试时生成新 ID。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 23. RPC 返回 OK 就能说明业务操作成功吗？

**合格**：区分 gRPC 传输状态与响应 `base_rsp` 业务状态；gRPC `OK` 只表示 RPC 通信完成，业务仍可能是 `NOT_LEADER`。**加分**：SDK 检查两层状态并据业务错误决定刷新路由/重试；RPC 超时未收到响应时，写结果可能未知。**追问**：超时但服务端已提交怎么办？**失分**：只检查 `grpc::Status::OK`。**依据**：`src/storage/handler/storage_service_impl.cpp`、`src/sdk/storage_client.cpp`。

### 24. 重试为什么可能让系统更忙、问题更严重？

**合格**：服务变慢导致超时，客户端重试会额外增加 Storage/Leader 和 Topo 压力，进而造成更多超时，形成负载放大。**加分**：项目已限制重试次数、路由刷新次数和总 deadline，并用指数退避；生产化可加 jitter、限流和熔断，观察重试率、成功率与尾延迟验收。**追问**：如何避免雪崩？**失分**：认为重试越多越可靠。**依据**：`src/sdk/client.cpp`；jitter、限流和熔断属于后续设计。

### 25. 读请求失败时，SDK 怎样把错误告诉调用方？

**合格**：`KEY_NOT_FOUND` 作为业务状态返回，不伪装成空值；`READ_INDEX_NOT_READY` 重试耗尽后映射为 `SDK_TRY_AGAIN`；路由错误按策略刷新并重试。**加分**：Get 不修改数据，不会有写入结果不确定的 `UNKNOWN`。**追问**：如果调用方需要弱一致读怎么办？**失分**：把所有读失败当成 key 不存在或空值。**依据**：`src/sdk/client.cpp`、`src/sdk/storage_client.cpp`、`src/storage/replica/replica.cpp`。

### 26. SDK 应记录哪些指标，才能看清请求表现？

**合格**：看三类指标：请求结果（成功/失败/`UNKNOWN`）、重试与路由（逻辑请求数、Storage RPC 尝试、缓存命中/刷新）、延迟（端到端、路由、RPC 的 p95/p99）。**加分**：区分逻辑请求与重试 attempt；切主时测从故障到稳定成功的时间，并观察成功率、`UNKNOWN`、重试量和尾延迟。**追问**：如何量化切主窗口？**失分**：只看平均 QPS。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/sdk/storage_client.cpp`、`docs/v0.1.0/retry.md`。

### 27. 客户端还拿着旧 `table_id` 时会发生什么？

**合格**：同名表删除后重建会分配新 `table_id`；旧缓存路由仍指向旧副本，遇副本/路由错误后 SDK 刷新并获取新路由，新表不会继承旧数据。**加分**：E2E 验证删表重建后旧 key 不可见。**追问**：如何用表代际版本防 ABA？**失分**：仅凭同名就认为是同一张表。**依据**：`src/catalog/store/catalog_store.cpp`、`src/sdk/route_cache.cpp`、`test/e2e/test_basic_chain.py`。

### 28. 哪些情况下客户端不该自动重试？

**合格**：参数错误、确定的业务错误不应重试；暂时性错误也受重试次数和总超时限制。写结果耗尽预算仍无法确认时返回 `UNKNOWN`。**加分**：邮件/支付等外部副作用需业务幂等键；本项目 Delete 不存在的 key 仍返回 `OK`（确保 key 不存在）。**追问**：Delete 不存在键的业务语义是什么？**失分**：所有失败都无限重试，或把 `UNKNOWN` 当成确定失败。**依据**：`src/sdk/client.cpp`、`src/storage/engine/map_engine.cpp`；外部副作用为设计推演。

## D. 分片、Topo 与副本控制（29–38）

### 29. SDK 怎样根据 Key 找到 shard？

**合格**：SDK 用固定哈希计算 `hash(key) % shard_count` 得到 shard，再查该 shard 路由；Topo 使用同一算法。`table_id` 标识表/路由，不参与 key 哈希。**加分**：shard 数建表时固定，改变后需迁移数据；多 shard 不能自动分散单个热点 key。**追问**：如何应对热点 key？**失分**：认为 table_id 参与哈希，或多 shard 会自动均衡热点。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`、`src/topo/service/route_service.cpp`。

### 30. Topo 为什么只把 Leader 地址作为写入入口发布？

**合格**：每个 shard 的写入由一个 Leader 统一排序；Topo 只发布恰有一个有效 Leader 的路由。**加分**：无 Leader 或最高 term 冲突时清除路由；不同 term 冲突时保留最高 term。切主期间可能暂时不可写，以避免发布不安全路由；Storage/Raft 仍会校验 Leader 身份。**追问**：多个不同 term Leader 上报怎么办？**失分**：随机选一个。**依据**：`src/topo/service/route_service.cpp`、`test/topo/service/route_reconcile_service_test.cpp`。

### 31. 节点心跳用来做什么？

**合格**：NodeAgent 定期向 Topo 上报节点及本地副本状态；Topo 更新健康/路由视图并返回副本管理指令。**加分**：心跳丢失不等于节点永久损坏；这与 Raft 副本间用于选主/复制的心跳不同，也不能证明写入已提交。**追问**：网络分区时双方视图为何不同？**失分**：把 Topo 心跳当作 Raft 心跳或提交确认。**依据**：`src/storage/node_agent/node_agent.cpp`、`src/topo/service/node_service.cpp`、`src/topo/service/replica_group_service.cpp`。

### 32. 为什么要分别记录期望状态和当前实际状态？

**合格**：desired 记录目标副本数/位置；observed 记录 Storage 心跳上报的副本状态和 Raft 成员角色。Reconciler 比较两者并多轮推进，例如目标 3 副本时，必须等 3 个副本 READY 且成为 voter 才算就绪。**加分**：异步操作可重试，控制面重启后能继续收敛。**追问**：目标与实际长期不一致时如何报警？**失分**：下发创建指令就当副本已就绪。**依据**：`src/topo/model/model.h`、`src/topo/reconcile/`、`src/topo/service/table_service.cpp`。

### 33. 扩容副本时为什么先把新副本设为 learner？

**合格**：新副本先以 Learner 加入，接收日志/快照但不参与投票和多数派；追到 Leader 当前日志位置后再提升为 Voter。**加分**：未追平就计入多数派可能影响提交与可用性。**追问**：快照传输期间日志继续增长怎么办？**失分**：副本一创建就当作健康 Voter。**依据**：`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_replication.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 34. 副本数缩到 0 时代表什么？

**合格**：缩容到 0 后无 KV 路由，读写返回 `ROUTE_NOT_FOUND`；Storage 删除副本及其持久化数据，扩容会创建新副本，不能假设旧数据保留。**加分**：保留数据需先备份；现有 E2E 验证 0 副本不可读写和扩回后可写，但未验证旧数据保留。**追问**：如何安全地缩到 0 并保留数据？**失分**：说零副本仍可读，或扩回后数据必然恢复。**依据**：`tools/e2e/cases/scale_to_zero_case.h`、`src/storage/replica/replica_manager.cpp`、`src/topo/service/table_service.cpp`。

### 35. 怎样避免同一个 shard 的副本落在同一故障域？

**合格**：只选目标资源池内在线且地址有效的节点；同 shard 不重复选节点，并优先分散 DC，再平衡节点副本数。**加分**：候选节点或 DC 不足会限制隔离效果；DC 标签须与真实部署一致，同机多进程不等于跨故障域容灾。**追问**：可用 DC 数不足怎么办？**失分**：仅凭不同 DC 标签就声称实现物理故障隔离。**依据**：`src/topo/selector/node_selector/node_selector.cpp`、相应测试。

### 36. Leader 切换后，路由什么时候会更新？

**合格**：切主后需经过 Raft 选举、NodeAgent 心跳上报、Topo 重建路由、SDK 刷新并重试；旧 Leader 可能先返回 `NOT_LEADER`。**加分**：Topo/SDK 后台任务的周期只是检查间隔，不是恢复时间保证；按故障发生到业务稳定成功测恢复窗口。**追问**：如何测切主期间的成功率和恢复时间？**失分**：把 Raft 选举时间当作业务恢复时间。**依据**：`src/topo/background/background.cpp`、`src/topo/main/main.cpp`、`src/sdk/route_cache.cpp`、`scripts/failover_bench.sh`。

### 37. Topo 或 Catalog 故障会影响哪些操作？

**合格**：Catalog 故障影响 DDL/元数据；Topo 故障影响取路由、路由刷新和拓扑调度。已有有效路由时 KV 可能暂时继续访问 Storage；路由失效或冷启动时则可能失败。**加分**：数据面能否写还取决于 Storage Raft 多数派；缓存不能替代控制面高可用。**追问**：如何给 Catalog/Topo 做高可用？**失分**：称控制面故障对业务完全无影响，或 Storage 数据立即丢失。**依据**：`src/sdk/route_cache.cpp`、`src/catalog/main/main.cpp`、`src/topo/main/main.cpp`、`README.md`。

### 38. 如果要在线拆分 shard，需要设计哪些步骤？

**合格**：当前不支持在线 split；设计上需版本化路由，复制旧 shard 数据并追平迁移期间的写入，再切换路由；旧路由请求应刷新/重试，并保留回滚方案。**加分**：定义迁移期间一致性、限速和完成证据。**追问**：如何避免复制期间的写入丢失？**失分**：直接改 `shard_count` 并重新取模。**依据**：`README.md` 当前限制、`src/sdk/route_cache.cpp`。

## E. Raft、一致性与成员变更（39–52）

### 39. Raft 选举能保证什么？

**合格**：候选者先经 PreVote，再在新 term 请求投票；日志足够新的候选者获当前 voter 多数票后成为 Leader。**加分**：选举不等于写入提交，每笔写仍需多数派确认；少数派旧 Leader不能提交，看到更高 term 后退位。**追问**：3 个 voter 中少数派能否选出可提交的 Leader？**失分**：认为任意节点可单独继续写，或 Leader 当选即代表数据已复制。**依据**：`src/storage/raft/core/raft_core_election.cpp`、`src/storage/raft/raft_membership.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 40. Raft 的 term、log index、commit index、apply index 分别表示什么？

**合格**：`term` 是选举任期，`index` 是日志位置；`commit_index` 是 Raft 已提交到的位置，`apply_index` 是状态机已执行到的位置。顺序为追加日志→多数派确认→commit→apply。**加分**：通常 `apply_index ≤ commit_index ≤ last_log_index`；重启从 `raft_meta`、WAL 和 Snapshot 恢复。**追问**：日志已写入 WAL 就一定提交了吗？**失分**：混淆追加、提交和 apply。**依据**：`src/storage/raft/`、`src/storage/replica/replica_applier.cpp`、`src/storage/persist/persist_engine.cpp`。

### 41. 为什么旧 term 的日志不能只因复制到多数派就算提交？

**合格**：旧任期日志即使复制到多数副本也不能直接宣布提交；Leader 需先让当前任期日志获多数派确认，之前的日志前缀才随之安全提交。**加分**：新 Leader 追加 no-op 建立当前任期的提交位置，ReadIndex 也依赖此条件。**追问**：当前任期 no-op 有什么作用？**失分**：认为多数副本有日志就一定已提交。**依据**：`test/storage/raft/core/raft_cluster_test.cpp` 的 Figure8 用例、`src/storage/raft/raft_replication.cpp`、`src/storage/raft/core/raft_core_election.cpp`。

### 42. PreVote 能解决什么问题，不能解决什么？

**合格**：PreVote 是正式选举前的探测；获得多数派预投票后才提升 term 并开始正式选举，减少隔离旧节点抬高 term 干扰活跃 Leader。**加分**：之后仍需日志足够新并获多数派正式选票；PreVote 不选出 Leader，也不解决控制面单点。**追问**：PreVote 接收者会因预投票请求提升 term 吗？**失分**：把 PreVote 当成正式选票或 Leader 身份。**依据**：`src/storage/raft/core/raft_core_election.cpp`、PreVote 用例。

### 43. Raft 怎样发现并修复冲突日志？

**合格**：Follower 用 `prev_log_index/term` 校验日志前缀；不匹配则拒绝，Leader 回退 `next_index` 重试。发现冲突时截掉并替换未提交后缀；日志已压进 Snapshot 时先安装 Snapshot，再复制后续日志。**加分**：已提交前缀不可被覆盖。**追问**：Follower 落后到 Leader 已压缩的日志之前怎么办？**失分**：不校验前缀、直接追加到尾部。**依据**：`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_log.cpp`、`src/storage/raft/raft_peer_progress.cpp`。

### 44. 为什么 Raft 多数派要达到 N/2 + 1？

**合格**：quorum=`floor(N/2)+1`，任意两个多数派有交集；3 个 voter 需 2 票、可容忍 1 个故障。**加分**：例如写入由 `{A,C}` 确认提交，A 故障后新选举多数派 `{B,C}` 与其交于 C；C 的日志新旧检查可阻止缺少已提交日志的 B 当选。4 个 voter 需 3 票、仍只容忍 1 个故障；5 个需 3 票、可容忍 2 个。Learner 不计入 quorum，跨 DC 确认会影响写延迟。**追问**：为什么 3 增至 4 未提升容错？**失分**：把 Learner 计入多数派。**依据**：`src/storage/raft/raft_membership.cpp`、Raft 集群测试。

### 45. Leader 崩溃后，为什么写请求可能返回 `UNKNOWN`？

**合格**：Leader 崩溃时，请求可能已经被多数派提交，只是响应没到客户端；也可能只存在于 Leader 本地，尚未提交，之后会被新 Leader 覆盖。客户端超时无法区分这两种情况，所以在重试预算耗尽后返回 `UNKNOWN`。**加分**：重试同一笔写入要复用 `request_id`，不能把超时当成确定失败。**追问**：为什么简单 Get 不能严格判定原请求？**失分**：把超时当成确定失败。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`、`docs/v0.1.0/retry.md`。

### 46. 项目的 Get 在什么条件下能保证线性一致？

**合格**：Get 确认本节点是 Leader、当前任期已有已提交日志，并获多数派确认；取 `read_index = commit_index`，apply 到 `apply_index ≥ read_index` 后再读 Map。**加分**：多数派不可达或 ReadIndex 未就绪时失败/稍后重试，不返回可能过期数据。**追问**：单副本时如何满足多数派？**失分**：只看本地 Leader 标记就读 Map。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/replica/replica.cpp`。

### 47. ReadIndex 和 Lease Read 有什么区别？

**合格**：ReadIndex 每次读都确认多数派；Lease Read 在多数派确认形成的租约有效期内可本地读，延迟较低。**加分**：Lease Read 的安全性依赖时钟/暂停假设；本项目实现 ReadIndex，未实现 Lease Read。**追问**：进程暂停或时钟误差如何影响租约安全？**失分**：把 ReadIndex 说成纯本地读，或声称项目已有 Lease Read。**依据**：`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/raft/core/raft_core_read.cpp`。

### 48. Raft 成员变化时，多数派应该怎么算？

**合格**：Quorum 按当前 Voter 集合计算，Learner 不投票、不计数；新副本追平后升为 Voter，配置变更经 Raft 日志生效。**加分**：3→4 个 Voter 后 quorum 从 2 变 3；3 缩到 2 后仍需 2 票，失去容忍 1 个故障的能力。成员变更需序列化、不能跳过 Learner 追赶。**追问**：3 voter 缩到 2 voter 时可容忍几个故障？**失分**：把 Learner 计入 quorum，或只改 Topo 目标就认为成员配置已变。**依据**：`src/storage/raft/raft_membership.cpp`、`src/storage/raft/core/raft_core_append.cpp`、成员变更测试。

### 49. 网络分区恢复后，怎样防止旧 Leader 破坏新日志？

**合格**：3 副本中 A 分区、B/C 选出更高 term 的新 Leader；A 恢复后见高 term 退位，新 Leader 按日志匹配修复 A 的未提交冲突后缀，已提交日志必须保留。**加分**：少数派旧 Leader不能提交；SDK 遇旧路由的 `NOT_LEADER` 会刷新路由，超时写可能返回 `UNKNOWN` 并须复用 request_id。**追问**：A 分区期间已成功返回的写能丢吗？**失分**：认为节点恢复时本地日志优先。**依据**：`src/storage/raft/core/raft_core_election.cpp`、`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_log.cpp`、`src/sdk/client.cpp`。

### 50. Topo 同时收到两个 Leader 报告时怎么办？

**合格**：双 Leader 上报可能是心跳延迟造成的观测冲突；Topo 对不同 term 保留最高者，最高 term 相同则清除可写路由。**加分**：路由不是写入许可，Storage/Raft 多数派才决定能否提交；SDK 遇 `NOT_LEADER` 刷新路由。已确认提交的写不能丢，超时未确认则为 `UNKNOWN`，用原 `request_id` 重试。**追问**：如何区分上报冲突与 Raft 安全性被破坏？**失分**：Topo 随机选 Leader，或把超时当确定失败。**依据**：`src/topo/service/route_service.cpp`、`src/storage/raft/raft_replication.cpp`、`src/sdk/client.cpp`、RouteServiceReconcile 测试。

### 51. 怎样测试 Raft 是否正确？

**合格**：协议测试覆盖选主、复制、少数派、崩溃切主、冲突修复、追赶和 Snapshot。**加分**：区分逐步 tick 模拟、并发提议测试、多进程 E2E 和 Maelstrom 故障注入；它们覆盖不同层次，不能互相替代。**追问**：如何验证线性一致历史？**失分**：只测 Put 后立即 Get，或把协议模拟说成真实并发测试。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`test/e2e/`、`tools/maelstrom_raft/`。

### 52. 为什么 Raft 不能自动保证所有业务数据都一致？

**合格**：Raft 保证单个 Raft 组的日志顺序与提交；业务仍需处理请求去重、确定性状态机和一致读。不同 shard 是独立 Raft 组，不自动组成事务。**加分**：跨 shard 转账可能一边扣款已提交、另一边入账未提交；本项目无跨 shard 事务和在线 split。**追问**：如何设计两个 shard 的原子更新？**失分**：认为 Raft 自动提供全局事务。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/sdk/client.cpp`、`README.md`。

## F. WAL、Snapshot 与恢复（53–62）

### 53. 为什么要先持久化 WAL，再更新状态机？

**合格**：先把日志写入 WAL 并持久化，再应用到状态机，才能保证崩溃后可从 WAL 重放尚未进入 Snapshot 的操作；若先改状态机、后写 WAL，崩溃可能造成状态已变化但日志丢失。**加分**：区分三个完成点：本机 WAL 写入并 `fsync` 成功是本地持久化；日志复制到多数派并满足 Raft 条件才是提交；已提交日志执行到 KV 才是状态机 apply。本地持久化不等于提交或 apply。`fsync` 失败时不能把持久化当作成功继续推进，应返回错误并进入副本故障处理。**追问**：如何处理 WAL 写入成功但多数派复制失败的日志？**失分**：认为写入 page cache 就等于在所有故障模型下持久，或把本地落盘等同于 Raft 提交。**依据**：`src/storage/persist/persist_engine.cpp`、`src/storage/replica/replica_applier.cpp`、`src/storage/replica/replica_loop.cpp`。

### 54. Snapshot 应保存哪些内容才能正确恢复？

**合格**：Snapshot 至少保存 KV 数据、状态机已应用日志的 index/term、请求去重记录，以及恢复 Raft 成员配置所需的元数据，分别保证数据状态、日志恢复位置、重试语义和成员关系能够恢复。**加分**：举例说明客户端写请求已执行但响应丢失时，重试应通过请求记录识别并返回原结果；若 Snapshot 丢失该记录，非幂等操作可能重复执行。Snapshot 必须先可靠持久化，再裁剪其边界之前的 WAL，确保崩溃恢复时总有一份完整状态可用。**追问**：Snapshot 与 WAL 裁剪顺序如何保证安全？**失分**：只序列化 KV Map，忽略 apply 位置、去重记录或成员配置。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp`。

### 55. Snapshot 和 WAL 的边界怎么定，旧日志何时能删？

**合格**：Snapshot 记录截至 `snapshot_index` 的完整状态，因此 WAL 中 `index <= snapshot_index` 的日志可以裁剪，`index > snapshot_index` 的日志必须保留以供恢复或追赶；剩余日志应从 `snapshot_index + 1` 连续开始，否则存在恢复缺口，不能静默跳过。应先可靠持久化 Snapshot，再裁剪旧 WAL。若 Snapshot 已落盘但裁剪前崩溃，恢复时可忽略 WAL 中边界以内的冗余记录；若先删 WAL、Snapshot 尚未可靠保存就崩溃，可能同时失去恢复所需的旧状态和日志。**加分**：说明写临时 Snapshot、原子替换和 WAL 重写各阶段崩溃时，恢复需检查 Snapshot/WAL 的完整性及 index 边界；项目恢复会过滤 `index <= snapshot_index` 的记录，并检查剩余 WAL 是否从边界后一条开始。**追问**：发现 Snapshot 与 WAL 之间有 index 缺口时，为什么不能直接继续 apply？**失分**：只按文件大小轮转而不看 index，或认为先裁剪 WAL 再写 Snapshot 也安全。**依据**：`src/storage/persist/persist_engine.cpp`、PersistEngine 测试。

### 56. WAL 末尾损坏时，哪些日志能截掉，哪些不能？

**合格**：恢复时按记录长度、校验信息和 index 连续性逐条读取；遇到不完整或损坏的尾部，保留此前完整日志并标记需要恢复。只有确认损坏部分未提交时，才可截断后继续；若可能涉及已提交日志，不能静默丢弃，应从健康副本追赶或进入故障处理。index 有缺口也不能跳过后继续 apply。**加分**：说明项目当前的 WAL 读取会在解码失败、部分记录或 index 不连续时报告错误；恢复流程保留有效前缀、设置 `need_recover` 并重写 WAL，但这一步本身不能证明被丢弃部分未提交。若多数派副本都损坏，可能没有可用来源恢复已提交数据，应说明系统恢复能力的边界。**追问**：如何判断损坏尾部是否可能包含已提交日志？**失分**：遇到 CRC/解码错误就清空全部 WAL，或静默丢弃可能已提交的数据。**依据**：`src/storage/persist/persist_engine.cpp`、`src/storage/persist/persist_engine.h`、`test/storage/persist/wal_crash_injection_test.cpp`。

### 57. 副本落后时，什么时候补日志，什么时候装 Snapshot？

**合格**：判断 Leader 是否仍保留落后副本缺失的日志：若保留，通过 `AppendEntries` 发送缺失日志；若日志已被 Snapshot 覆盖并从 WAL 裁剪，则先安装 Snapshot，再通过 `AppendEntries` 补齐边界之后的日志。Snapshot 安装完成只表示副本恢复到该 Snapshot 的 index，不代表已追到最新；Leader 传输期间可能继续提交新日志，因此副本还需追赶到所需提交位置后才能安全升为 voter。**加分**：说明 Snapshot 分片接收需校验会话与 offset 连续性；中断后应按协议重试或重新开始传输，不能把未完成的 Snapshot 发布为可用状态。**追问**：如何确认安装 Snapshot 的副本已追到可以安全升 voter 的位置？**失分**：认为 Snapshot 安装完成就等于最新，或忽略 Snapshot 边界后的日志。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`test/e2e/test_basic_chain.py`。

### 58. 为什么 KV 在内存中运行，重启后仍能恢复？

**合格**：区分运行时存储与崩溃恢复：KV 状态由 `MapEngine` 保存在内存中，运行时读写直接操作 Map；WAL 和 Snapshot 写入磁盘，用于重启后重建状态，恢复时需要把数据重新加载到内存。因此这是具备持久化恢复能力的内存引擎，不是直接在磁盘上存储和查询 KV 的磁盘引擎，数据容量仍受内存限制。**加分**：说明它与 RocksDB/LSM 在磁盘数据组织、索引、压缩和容量模型上的差异。**追问**：数据超过内存时需要怎样的磁盘存储引擎或容量管理方案？**失分**：称 Map 完全不落盘，或称项目已实现 RocksDB/LSM 式磁盘 KV 引擎。**依据**：`src/storage/engine/map_engine.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/replica/replica.cpp`、`src/storage/persist/persist_engine.cpp`。

### 59. 生成 Snapshot 时有并发写入，怎样保证快照一致？

**合格**：Snapshot 必须对应明确的状态机 apply index/term。项目在持有 `state_machine_mutex` 时调用 `capture_snapshot`，在同一临界区复制 KV、请求去重记录和 apply 位置，阻止并发 apply 造成数据与 index 不匹配；随后释放状态机锁再写 Snapshot 文件，并在 Raft 锁下读取成员配置。**加分**：说明捕获期间复制大 Map 仍会阻塞 apply 和相关访问，增加尾延迟；可考虑 MVCC、一致性视图或 Copy-on-Write 缩短阻塞。**追问**：怎样改为增量快照并保持一致性？**失分**：边遍历 Map 边无锁写文件，却声称快照与 apply index 一致。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 60. 副本恢复期间，为什么暂时不对客户端提供读写？

**合格**：这里的恢复指某个副本因重启时发现 WAL 损坏、Snapshot 与 WAL 有缺口等本地状态问题而进入 `RECOVERING`，不特指 Leader 崩溃。恢复副本不应对客户端提供读写服务，接口返回 `IS_RECOVERING`；但仍需接收 Leader 的 `AppendEntries` 或安装 Snapshot 等 Raft 内部恢复消息。项目会将恢复中的 Raft Core 退回 Follower 并停止选举计时器；通常客户端读写由 Leader 承接，因此还需避免把恢复副本路由为服务节点。**加分**：说明恢复完成依赖 Raft 复制或 Snapshot 安装，而不是仅完成 Map 加载，并与健康检查、路由摘除协同。**追问**：如果只有一个健康副本怎样处理可用性？**失分**：把本地副本恢复等同于 Leader 故障切换，或认为恢复副本应拒绝所有 Raft 消息。**依据**：`src/storage/replica/replica.cpp`、`src/storage/raft/core/raft_core_recovery.cpp`、`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/core/raft_core_snapshot.cpp`。

### 61. 怎样验证重启后数据和 Raft 状态都恢复正确？

**合格**：先写入并确认成功，再停止、重启服务并验证 KV 数据恢复；同时检查 Snapshot apply index/term、后续 WAL 日志、Raft 成员配置及 request ID 去重记录。**加分**：覆盖部分 WAL 记录、Snapshot 已落盘但 WAL 尚未裁剪、Snapshot 与后续 WAL 并存等崩溃点。验证重启后的幂等性时，用相同 `request_id` 重试并确认它不会被当作新请求重复处理；再用相同 ID 搭配不同请求内容，验证冲突按设计被拒绝。**追问**：如何证明幂等在重启后仍生效？**失分**：只看进程成功启动，或只检查普通 Put/Get 而不验证恢复边界和请求去重。**依据**：`test/storage/persist/persist_engine_test.cpp`、`test/e2e/test_basic_chain.py`、`test/storage/replica/replica_test.cpp`、`test/storage/raft/state_machine/kv_state_machine_test.cpp`。

### 62. 如果把当前内存 Map 换成 RocksDB，应该先改什么？

**合格**：基于现有 `KVEngine` 接口实现 RocksDB 引擎，并先划清日志职责：Raft WAL 保留共识日志、复制和追赶职责；RocksDB WAL 负责本地引擎写入的崩溃恢复。两者作用不同，但会增加写入开销。状态机 apply 时应保证 KV、request ID 去重记录和 apply index 一致，例如放入同一个 RocksDB `WriteBatch` 原子提交；恢复时依据已应用位置决定如何继续重放 Raft 日志，避免漏写或重复应用。还需重新设计 Snapshot 与恢复映射，保存匹配的 apply index/term、成员配置及去重记录，并规划旧 Map Snapshot 的迁移兼容。**加分**：补充 RocksDB checkpoint/一致性迭代方案，以及崩溃注入、重启恢复、性能和容量测试计划。**追问**：如何避免 Raft WAL 与 RocksDB 状态在崩溃时失配？**失分**：只替换 `MapEngine` 类名，未定义两套 WAL、apply 原子性和 Snapshot/迁移方案。**依据**：当前接口 `src/storage/engine/kv_engine.h`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp`，限制见 `README.md`。

## G. 测试、性能与部署（63–72）

### 63. 单元测试、端到端测试和 Maelstrom 分别验证什么？

**合格**：单元测试验证单个模块的逻辑与边界，运行快、便于定位，适合每次提交运行；E2E 启动多个服务进程，验证真实 RPC 链路、模块集成及重启/故障切换等场景；Maelstrom 对 RaftCore 施加并发工作负载并注入网络分区等故障，检查线性一致性等协议属性。三者覆盖层次不同、互相补充，任何一类通过都不能替代另外两类。**加分**：说明 E2E 适合持续集成或发布前运行，Maelstrom 故障压力测试可定期运行或在 Raft 核心变更后运行；项目脚本会在检测到 Maelstrom 时运行无故障和 partition 场景。**追问**：单测和 E2E 都通过，为什么仍需要 Maelstrom 故障测试？**失分**：只报测试数量，或把某一类测试通过当作整体正确性的证明。**依据**：`test/`、`test/e2e/`、`scripts/run_test.sh`、`tools/maelstrom_raft/`。

### 64. 为什么最小集群验收要用三副本？

**合格**：三副本 smoke 可以覆盖集群正常运行时的 Leader 选举、日志复制和多数派提交路径；单副本只能验证服务启动、建表和基础 CRUD，不能验证选主、复制、多数派或节点故障处理。项目的三副本验收检查建库建表、写入读取、覆盖、删除和重建表等基本链路。**加分**：说明普通 smoke 没有主动停节点或制造网络分区，因此不能证明故障容错，也不覆盖批量故障和生产负载；这些场景需由专门 E2E 或故障注入测试覆盖。**追问**：单副本 smoke 能证明什么、不能证明什么？**失分**：把三副本正常流程验收等同于已验证故障容错或完整分布式正确性。**依据**：`scripts/verify_project.py`、`test/e2e/test_basic_chain.py`。

### 65. 怎样做 Benchmark 才不会得出误导结论？

**合格**：报告测试环境（CPU、内存、操作系统、构建类型、进程部署拓扑）、负载条件（请求数、线程数、分片数、副本数、键/值大小、读写比例）和结果（成功率、成功 QPS、平均延迟及 p95/p99）；区分尝试吞吐量与成功吞吐量，避免失败请求被 QPS 掩盖。**加分**：先预热、重复多轮、保留原始数据并分析波动；说明仓库历史约 9,800 Put QPS 来自单机本地集群，只能用于相似环境和负载下比较，不能直接用于跨机容量规划。**追问**：本仓库历史 9,800 Put QPS 能否用于跨机容量规划？**失分**：脱离负载条件引用单个峰值，或只报 QPS、不报告延迟和成功率。**依据**：`docs/v0.1.0/benchmark/README.md`、`tools/bench/`。

### 66. Put 的 p99 延迟升高时，应该从哪里开始排查？

**合格**：先确认端到端 Put p99，再沿 SDK 路由与 RPC、Storage handler、Leader 排队、Raft 复制与提交、WAL 写入/`fsync`、状态机 apply 分段对比耗时，找出变慢环节；指标对比应使用相同负载和时间窗口。**加分**：逐个调整并发数、副本数、Value 大小等参数，结合 CPU、磁盘、网络和锁竞争指标定位根因；平均值稳定而 p99 升高说明少数请求出现长尾等待，可能由排队、慢 `fsync`、网络抖动或锁竞争导致，但不能单凭 p99 判断根因。**追问**：p99 上升而平均值稳定意味着什么？**失分**：未分段测量就直接归因于 Raft，或一次改变多个负载参数导致无法归因。**依据**：`src/sdk/client.cpp`、`src/sdk/storage_client.cpp`、`src/storage/handler/storage_service_impl.cpp`、`src/storage/replica/replica_loop.cpp`、`src/storage/persist/persist_engine.cpp`、`scripts/bench_metrics.sh`、历史报告。

### 67. 读和写的性能瓶颈有什么不同？

**合格**：写请求需要 Raft 提议、日志持久化、复制到多数派并提交，再由状态机 apply；强一致 Get 虽从内存 KV 取值，也要通过 ReadIndex 确认当前 Leader，并确保状态机已 apply 到安全读位置，但不需要为这次读持久化一条新的业务日志。两者都可能受 SDK/RPC、网络、队列和锁影响。**加分**：在相同环境与负载下比较读写的成功率、成功 QPS 及 p50/p95/p99，并结合阶段耗时定位差异；p99 是 99% 请求延迟不超过的值，用来观察长尾，不能单凭它判断根因。弱一致 Follower Read 可减少 Leader 确认路径开销，但可能读到落后数据。**追问**：弱一致 follower read 会改善什么、牺牲什么？**失分**：认为 Get 纯内存所以没有网络或一致性确认成本，或只用平均延迟代表尾延迟。**依据**：`src/storage/replica/replica.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/persist/persist_engine.cpp`。

### 68. 为什么增加 shard 后吞吐不一定同比增长？

**合格**：增加 shard 能提高独立分片的并行度，但客户端、单机 CPU/磁盘/网络和锁等仍是共享瓶颈；热点 shard、热点 key 或 Leader 分布不均也会限制吞吐。多个 Raft 组还可能竞争同一台机器的资源，因此 shard 增加不保证 QPS 线性提升。**加分**：固定其他负载参数，扫描 `shard_count` 与线程数，观察吞吐、p99 和资源指标；本仓库特定单机 Put Benchmark 中 shard 从 1 增至 2、4、8 时，成功 QPS 约从 10,249 降至 9,058、6,995、6,621。应说明这是特定环境和负载下的结果，不代表增加 shard 普遍会降低吞吐。拆散单热点 key 可考虑分片或加盐，但会改变读聚合成本与业务语义。**追问**：单热点 key 如何拆散？要说明业务语义与读聚合代价。**失分**：声称 shard 翻倍 QPS 必翻倍，或把一次单机 Benchmark 结果当作普遍规律。**依据**：`docs/v0.1.0/benchmark/benchmark_put.md`。

### 69. Leader 故障切换后，怎样测客户端何时恢复成功？

**合格**：持续发送写请求并记录 kill Leader 的时刻、故障后首个成功请求时间，以及故障窗口内逻辑请求的成功/失败/`UNKNOWN` 数和 p95/p99；按逻辑请求统计，避免将 RPC 重试重复计数，且说明 `UNKNOWN` 表示客户端无法确认写入结果。**加分**：固定其他参数对比不同重试预算，区分 Raft 选举完成与 SDK 路由/重试后业务请求恢复；引用历史结果时说明测试条件，例如 `max_retries=1` 时故障后请求全部失败，`max_retries=3` 时仍约有 33.98% 失败，首次恢复窗口约 1.38–1.69 秒，这只适用于报告中的环境和参数。**追问**：为什么 Raft 已选出新 Leader，业务请求仍可能失败？**失分**：只报告选举耗时，或把 `UNKNOWN` 当作确定未提交。**依据**：`scripts/failover_bench.sh`、`docs/v0.1.0/retry.md`。

### 70. 为什么测试要使用独立端口和数据目录？

**合格**：测试使用独立端口，避免与演示服务冲突或客户端连错实例；使用独立数据目录，避免旧 WAL、Snapshot 和元数据污染结果，并可安全清理测试状态。服务应通过本次启动的进程句柄停止，避免误杀其他服务。**加分**：指出当前 E2E 使用固定端口，若要并行运行多套测试，需为每个实例分配独立或动态端口及独立数据目录；项目清理逻辑只删除 `BUILD_DIR/e2e_test`，演示数据放在 `build/demo`。**追问**：并行 E2E 如何改用动态端口和隔离目录？**失分**：让测试和演示共用端口/数据目录，或用全局 kill 清理所有同名服务。**依据**：`scripts/verify_project.py`、`test/e2e/cluster.py`、`scripts/internal/local_cluster.py`。

### 71. CI 构建成功但本机启动失败，怎样一步步排查？

**合格**：区分构建成功与本机可运行，依次检查运行时依赖和构建产物、构建目录及 Generator、配置路径与内容、端口占用、数据目录、服务日志和请求错误码；按 Topo→Catalog→Storage→Client 的依赖顺序逐层启动，核对进程状态与监听端口。**加分**：说明 `scripts/build.sh` 默认使用 Ninja，已有 `build-make` 若配置为 Unix Makefiles，就不能用 Ninja 直接复用；应指定匹配的 `GENERATOR`，或使用独立构建目录。配置中的相对路径以项目根目录为基准；排查时保留日志和旧数据作为故障证据，不盲目清理。**追问**：为什么 `build-make` 不能直接按默认 Ninja generator 复用？**失分**：只说“重新安装依赖”，或未定位具体失败层就删除数据和日志。**依据**：`scripts/build.sh`、`scripts/internal/local_cluster.py`、`conf/README.md`。

### 72. 要把项目写进简历，需要准备哪些证据？

**合格**：把项目能力与个人贡献分开举证：能演示或复现的，说明本机环境和验证范围；仓库有自动化用例但本次未重跑的，表述为“项目有相应用例”；能定位代码但未独立验收的，说明实现入口及验证边界；历史 Benchmark 标明机器、拓扑、负载和数据来源，不说成刚刚重跑或生产容量；设计推演明确标注为计划而非已交付。**加分**：准备一个亲自排查的问题、一项口径完整的量化结果，以及一个当前限制和改进方案；能说明个人实际负责的部分。**追问**：历史 benchmark 是否是你本人在本机重跑？**失分**：把仓库功能都说成个人完成，或复制 README 数字却不了解测试环境和负载。**依据**：[证据与边界](证据与边界.md)。

## H. 推荐架构、AI/Agent 与系统设计（73–84，均为设计推演）

### 73. 推荐系统里哪些数据适合放 KV，哪些不适合？

**合格**：将 RaftBox 作为在线小规模、按 Key 访问的配置或状态存储进行评估，例如实验开关、用户少量实时状态/特征；Raft 强一致适用于需要副本间一致的状态，但要承担复制与确认成本。候选召回、向量相似度搜索和离线训练/大规模行为日志应交给倒排/ANN、数据湖或流批处理等专用系统。**加分**：按吞吐、延迟、一致性、容量增长和 TTL 需求设准入标准；指出当前 KV 是内存 Map、数据容量受内存限制，分片数建表时固定且无动态 split/rebalance，也尚无通用 TTL/过期清理能力。明确这属于架构推演，不代表项目已集成推荐链路。**追问**：为什么用户实时特征可能需要 TTL？**失分**：声称 RaftBox 已是完整推荐架构，或把尚未实现的 TTL、动态分片说成当前能力。**依据**：当前能力/限制见 `README.md`，推荐系统场景为设计推演。

### 74. 按 `user_id` 分片存特征，可能遇到什么问题？

**合格**：当前稳定哈希按 Key 将数据映射到固定 shard；以 `user_id` 为 Key 时，同一用户的数据集中在一个 shard，少数高频用户会造成热点，而普通哈希无法拆分单个超大用户。增加副本数不能分散同一 Raft 组的 Leader 写入负载。**加分**：先观测 Top 用户及各 shard 的请求量、延迟和资源使用，再考虑按特征拆 Key、缓存或按业务维度分桶/加盐；说明分散数据会增加读聚合、缓存失效处理及跨 shard 更新的一致性复杂度，且当前没有动态 split/rebalance。**追问**：迁移分桶规则如何兼容旧读？**失分**：只增加副本数就声称写热点已解决，或忽略拆分后读聚合和一致性代价。**依据**：哈希路由 `src/common/stable_hash.h`；动态拆分与缓解方案为设计推演。

### 75. 推荐系统的配置数据都需要强一致吗？

**合格**：按错误代价和陈旧容忍度分级：风控规则/安全开关需要严格的发布保证；实验配置、部分实时特征可定义短暂陈旧窗口；离线快照通常可接受有界延迟，但需标注版本与生成时间。强一致读能降低读到旧状态的风险，却需要 Leader/多数派确认，并可能在多数派不可达时失败。**加分**：为各类数据定义陈旧窗口、故障降级、审计与回滚；配置采用版本化和分阶段发布，确认服务就绪后再切换生效版本，避免不兼容的新旧配置混用。项目 ReadIndex 可用于说明强一致读的确认成本；推荐业务分级与发布流程属于设计推演。**追问**：配置发布时如何防止半数服务用新旧版本混合？**失分**：所有数据都要求最强一致或都可最终一致，或把设计推演说成项目已实现能力。**依据**：`src/storage/raft/core/raft_core_read.cpp`；业务分级与版本化发布为推演。

### 76. 目标是 10 万 QPS、p99 10 ms，怎样验证能否达到？

**合格**：先把目标定义成明确负载与 SLO：读写比例、key/value 大小、热点分布、数据量、部署地域/网络、复制数、可用性与故障条件；要求在持续 100,000 成功 QPS 下满足 p99 ≤ 10 ms，并同时约定错误率和运行时长。现有单机历史 Benchmark 不能直接外推到跨机容量。**加分**：从单 shard/单节点基线开始，逐层增加并发、shard 和机器，在真实网络与副本数下压测，观察成功 QPS、p99、资源饱和点和故障时表现；据此建立容量模型、估算 Leader/副本和机器数量，并预留扩容及节点故障余量。仓库历史单机 Put 约 9,800 成功 QPS、p99 约 5.6 ms，只是特定机器、拓扑和负载下的数据，不能简单乘机器数承诺 10 万 QPS。**追问**：只看平均延迟为什么不够？**失分**：忽略负载与故障条件，或按单机 QPS 线性乘机器数直接承诺。**依据**：`docs/v0.1.0/benchmark/`；10 万 QPS、p99 10 ms 为目标推演。

### 77. 多机部署时怎样放置副本并实现跨机房容灾？

**合格**：定义机器、机架、可用区等独立故障域，并在 Topo 中准确设置节点/DC 标签，让同一 Raft 组副本尽量分散；标签错误或所有节点使用同一标签无法实现预期隔离。跨地域写需等待 Raft 多数派确认，远距离网络 RTT 会增加写延迟，副本布局需权衡容灾范围与延迟。**加分**：说明节点选择器会倾向于分散 DC，但不能替代正确的物理部署；在真实多机网络下测试 RTT、磁盘、Leader 故障切换和副本恢复；Catalog、Topo 等控制面也要单独设计高可用、配置与服务发现，单机多进程 Benchmark 不能证明跨机容灾。**追问**：跨地域同步多数派如何影响写延迟？**失分**：只把配置 IP 从 127.0.0.1 改成远端，或假设设置 DC 标签就自动具备机房级容灾。**依据**：`src/topo/selector/node_selector/node_selector.cpp`、`README.md`；多机部署与容灾验证为设计推演。

### 78. Agent 调用工具时，怎样避免重试造成重复操作？

**合格**：为每个逻辑工具操作生成稳定幂等键，持久化请求参数、操作状态（如待执行/执行中/成功/结果未知）和工具返回结果；超时按结果未知处理，重试沿用同一键，使工具端能识别重复请求并返回已有结果。相同键若对应不同参数应拒绝复用。**加分**：指出外部副作用已发生而 Agent 尚未来得及记录成功时崩溃，会形成不确定窗口；若工具不支持幂等键，需查询外部状态、执行补偿或人工确认，不能仅靠本地记录保证 exactly-once。**追问**：模型重新规划后参数改变可复用同一 ID 吗？**失分**：超时后生成新键盲目重试支付/发信，或声称本地去重即可保证外部工具恰好执行一次。**依据**：借鉴 `src/sdk/client.cpp` 的 request ID 与 UNKNOWN、`src/storage/replica/replica_loop.cpp` 的请求去重；Agent 集成为设计推演。

### 79. 当前 RaftBox 能不能存 Agent 会话？还缺什么？

**合格**：从 API 看可将序列化会话状态作为 `bytes` KV 存储，但这不代表当前系统是专用会话存储；需评估单条 value 大小、总容量、查询模式、权限、TTL 和高可用。当前没有专用会话模型或通用 TTL，KV 引擎为内存 Map，数据恢复后需重新加载到内存。**加分**：为长会话设计 `session_id`/版本化 Key，避免每轮重写整个 value；可将摘要/检查点与原始消息分层或按消息增量存储，同时处理顺序、幂等、过期清理和恢复一致性。明确这属于适配设计，不代表已集成 Agent SDK。**追问**：长对话状态如何避免每轮重写整个 value？**失分**：声称当前已有会话模型、TTL 或 LangChain/Agent SDK 集成，或忽略拆分记录后的顺序与一致性问题。**依据**：`proto/storage.proto`、`README.md`；会话存储集成为推演。

### 80. Agent 长任务中断或重试后，怎样从上次进度继续？

**合格**：持久化任务阶段、输入版本、每步结果和外部工具调用幂等键；重启后从最后一个可验证检查点继续。区分内部计算与外部副作用，超时按结果未知处理，先查询状态或复用同一幂等键重试，不能盲目重做。**加分**：用持久化租约标记 Worker 所有权，并以递增版本号/fencing token 阻止过期 Worker 继续写；每步设计为幂等，并对无法确认的外部副作用支持补偿或人工处理。Catalog/Topo reconcile 可类比持久化状态驱动的查询、重试与收敛，但 Agent 长任务恢复属于设计推演。**追问**：两个 Worker 同时恢复同一任务怎么办？**失分**：只依靠进程内锁，或把外部工具调用描述成可由本地状态保证 exactly-once。**依据**：借鉴 `src/catalog/background/table_reconciler.cpp`；Agent 集成为设计推演。

### 81. 什么情况下选 KV、关系库、缓存或向量库？

**合格**：按访问模式与数据语义选型：已知 Key 的在线点查/更新适合 KV；需要事务、约束、关联或复杂条件查询适合关系库；可重建的热点数据适合缓存，但需设计过期、失效和回源；向量相似度近邻检索适合向量库。RaftBox 当前是内存 Map 加 WAL/Snapshot 恢复的 KV，不是关系库、缓存或向量检索系统的替代品。**加分**：多存储组合时定义数据源、更新顺序、失败重试和重建策略；同步在线特征时使用版本/更新时间比较，避免旧值覆盖新值，并为重试设计幂等去重。**追问**：在线特征从离线表同步到 KV 如何防旧版本覆盖新版本？**失分**：认为一套 KV 能解决所有查询，或忽略缓存失效、双写失败和跨存储一致性。**依据**：当前接口 `src/storage/engine/kv_engine.h` 与限制见 `README.md`；架构选型为推演。

### 82. 一次操作要更新两个 shard，怎样做到原子生效？

**合格**：当前 API 只有单条 KV 操作，每个 shard 的 Raft 只保证本组日志一致，不提供跨 shard 原子性；跨 shard 更新可能部分成功。先评估能否把相关数据放在同一 shard；否则按业务语义选择分布式事务（如两阶段提交）或 Saga。**加分**：说明两阶段提交需要持久化协调决议、参与者准备状态及崩溃恢复，协调者故障时参与者可能等待；Saga 通过补偿处理部分失败，但允许中间状态且补偿本身也可能失败。比较强原子性、可用性和实现复杂度。**追问**：两阶段提交协调者崩溃怎么办？**失分**：称每个 shard 有 Raft 所以跨 shard 自动原子，或把 Saga 补偿说成瞬时原子提交。**依据**：当前 API 见 `proto/storage.proto`；跨 shard 事务为设计推演。

### 83. 如果给 KV 增加 TTL（过期时间），需要考虑什么？

**合格**：区分 KV TTL 与 `request_id` 去重 TTL。KV 写入时记录过期时刻，读时按语义返回过期状态，后台清理器再通过 Raft 复制删除；过期元数据必须进入 WAL/Snapshot，保证重启恢复一致。不能让各副本在 apply 时按本地时钟独立决定删除。**加分**：说明 `request_id` TTL 定义去重窗口，过期后迟到重试可能被当作新请求，因此窗口需覆盖客户端重试和结果不确定时间；讨论持久化墙上时钟与单调时钟的用途及跨机偏差。**追问**：过期记录在 Snapshot 恢复后怎么处理？**失分**：只在 Map 里开本地定时器，或忽略去重窗口过期后的重复执行风险。**依据**：`README.md` 的 request ID 限制；TTL 实现为设计推演。

### 84. 如果重新设计项目，你会优先改哪一项？

**合格**：从项目已知限制中按目标优先选择一项（如 Map 内存容量、控制面单点、固定 shard 数或 request ID 无 TTL），说明现状证据、业务影响和优先级，不把所有改造都说成首要任务。**加分**：给出可回滚的最小交付切片与量化验收；例如为降低容量受内存限制的影响，先让 RocksDB 实现现有 `KVEngine` 接口，再明确 Raft WAL、引擎 WAL、Snapshot/恢复边界，验证崩溃恢复、旧数据兼容及相同负载下的容量/吞吐/p99。**追问**：最小可交付切片和成功判据是什么？**失分**：只说“微服务化、云原生化”，或同时承诺所有方向却没有优先级、迁移方案和验收标准。**依据**：`README.md`、`docs/版本.md`；改造方案为设计推演。

## I. 故障排查题（85–94）

### 85. `wait_table` 一直不成功，先查什么？

**合格**：先看 Catalog 表状态与 `last_error_msg`，再检查 Topo 是否收到目标规格、健康 Storage 节点是否足够、副本是否创建完成、Raft 是否选出 Leader、路由是否可写。Catalog 状态包括 `ADDING`、`NORMAL`、`FAILED`、`ALTERING`、`DROPPING`、`DELETED`；建表主要从 `ADDING` 收敛到 `NORMAL`。注意 Topo 的 `CREATING`、`RESIZING`、`READY` 是副本/路由收敛阶段，不是 Catalog 表状态。**加分**：按建表流程定位卡在节点选择、创建副本、成员变更还是路由发布；结合服务日志和错误信息区分节点不足与 Leader 未选出。**追问**：如果 Catalog 一直是 `ADDING`，怎么判断卡在哪一层？**失分**：只重启所有服务，或混淆 Catalog 状态和 Topo 阶段。**依据**：`src/catalog/model/`、`src/catalog/background/table_reconciler.cpp`、`src/topo/service/table_service.cpp`、`src/topo/service/route_service.cpp`。

**口述回答**：“`wait_table` 一直超时，说明表还没有进入 `NORMAL`。我会先查询 Catalog 中的表状态和 `last_error_msg`，再沿建表链路检查 Topo 是否收到建表目标、健康 Storage 节点是否足够、副本是否创建完成、Raft 是否选出 Leader，以及每个 shard 是否已有可写路由。Catalog 的表状态包括 `ADDING`、`NORMAL`、`FAILED`、`ALTERING`、`DROPPING` 和 `DELETED`；建表主要是从 `ADDING` 收敛到 `NORMAL`。如果一直停在 `ADDING`，我会继续定位副本创建或路由收敛卡在哪一步；如果是 `FAILED`，优先看错误信息。还要区分 Catalog 状态和 Topo 阶段：Catalog 描述表的 DDL 状态，Topo 的 `CREATING`、`RESIZING`、`READY` 描述副本和路由的收敛进度。”

### 86. Put 返回 NOT_LEADER，但 Topo 仍给旧端点，怎么办？

**合格**：`NOT_LEADER` 表示请求到达的节点不是当前 Leader；SDK 应刷新路由并在重试次数、总超时预算内重试。排查 Leader 变化、Storage 心跳上报、Topo 路由 reconcile 和 SDK 路由缓存的传播链路。**加分**：同一逻辑写入的重试始终复用同一个 `request_id`；若遇到 `RPC_ERROR`、`NOT_YET_COMMIT` 等结果不确定的情况，预算耗尽后应按 `UNKNOWN` 处理，不能换 ID 盲目重试；结合旧/新 Leader 的 term 和时间戳还原事件顺序。**追问**：旧 Leader 已提交但回包丢失怎么办？**失分**：无限重试、换新 ID 重试，或把 Topo 路由更新延迟直接当成数据丢失。**依据**：`src/sdk/client.cpp`、`src/topo/service/route_service.cpp`。

**口述回答**：“Put 返回 `NOT_LEADER`，但 Topo 还返回旧端点，通常是 Leader 已经切换，而心跳上报、Topo 路由更新或 SDK 缓存刷新还没有完成。我会先确认当前 Leader 和 term，再沿着 Storage 心跳到 Topo reconcile、再到 SDK 路由刷新的链路检查日志和时间线。处理上，SDK 对 `NOT_LEADER` 刷新路由，并在重试次数和总超时预算内重试；同一逻辑写入的每次尝试都沿用同一个 `request_id`。如果遇到 RPC 超时或 `NOT_YET_COMMIT`，写入结果可能无法确认，预算耗尽时应返回 `UNKNOWN`，之后仍用原 `request_id` 重试，避免重复执行。”

### 87. 三副本中一台宕机，写入突然全部超时，怎么查？

**合格**：确认当前 shard 的实际 voter 成员和可达多数派，检查宕机节点是否为 Leader、选举状态、日志复制/提交，以及 WAL/`fsync` 是否异常。三个 voter 的配置下，剩余两台只有在属于同一 voter 配置且能够通信时才构成多数派。**加分**：区分多数派不可达、Leader 选举中、日志无法提交、SDK 使用旧路由、Topo 路由未更新和资源饱和；对照 term、日志/commit index、RPC 错误与 metrics 还原时间线。**追问**：如果剩余两台其实不在同一个 voter 配置中呢？**失分**：直接认定“三副本可容忍一台故障，所以写入一定成功”。**依据**：`src/storage/raft/`、`src/sdk/client.cpp`、`src/topo/service/route_service.cpp`。

**口述回答**：“我会先确认这个 shard 当前的 Raft voter 配置和可达多数派，而不是只看配置上写着三副本。三个 voter 时，剩下两台必须属于同一个 voter 配置并且彼此可通信，才能形成多数派。然后确认宕机的是不是 Leader：如果是，就看新 Leader 是否选出以及选举期间的请求失败；如果已经有 Leader，就检查日志复制和 commit index 是否推进，并查看 WAL 写入、`fsync`、网络和 RPC 是否异常。同时检查 SDK 是否还在使用旧路由、Topo 是否收到心跳并更新路由。最后结合 term、日志索引、错误日志和 metrics 还原时间线，区分是多数派问题、选举问题、持久化变慢、路由滞后还是资源饱和。”

### 88. Get 返回旧值，如何判断是 bug？

**合格**：先确认 Put 是否明确返回成功、读写是否针对同一张表和同一个 key；再检查表是否重建、是否使用旧路由，以及 ReadIndex 确认和状态机 apply 是否追上安全读位置。**加分**：Put 返回 `UNKNOWN` 或超时不能当成已提交前提；并发读写时收集完整操作历史，验证是否存在符合线性一致性的执行顺序。**追问**：怎样采集足够的并发历史？**失分**：只看某个副本的本地 Map，或把 `UNKNOWN` 当成写入失败/成功。**依据**：`src/storage/replica/replica.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/sdk/client.cpp`。

**口述回答**：“我会先确认前提：Put 是否明确返回成功，Get 是否针对同一张表和同一个 key。如果 Put 只是超时或返回 `UNKNOWN`，写入可能已经提交，也可能没有，不能把它当成已成功的写来判断。确认前提后，我会检查是否有表重建或旧路由，再看 Get 是否经过 ReadIndex 多数派确认，并且状态机的 apply index 是否追上 read index。如果这些条件都正常，我会收集并发操作的开始和结束时间、请求结果及 request ID，验证是否存在合法的线性化顺序。不能只看某个副本的本地 Map，就断定读旧值是 bug。”

### 89. 重启后部分键丢失，怎么定位？

**合格**：先确认受影响的 shard、数据目录和 `table_id`，再检查 Snapshot 索引边界、WAL 记录/CRC，以及 `commit_index`、`apply_index` 是否一致。**加分**：先复制数据目录和日志保留现场；区分已提交日志损坏与未提交尾部损坏，并结合重启前 Put 的返回结果判断数据是否曾明确确认。**追问**：已提交日志的 CRC 损坏和未提交尾部损坏有何区别？**失分**：立即删除 WAL、覆盖现场或反复重启。**依据**：`src/storage/persist/persist_engine.cpp`、`src/storage/replica/replica.cpp`。

**口述回答**：“重启后发现部分键丢失，我不会先删 WAL 或反复重启，而是先保留并复制现场数据，确认受影响的 shard、数据目录和表的 `table_id`，排除读错目录或删表重建。然后检查 Snapshot 的索引边界和加载结果、WAL 中相关记录及 CRC，并对比 `commit_index` 和 `apply_index`，确认已提交的日志是否在恢复后正确 apply。已提交日志损坏和未提交尾部损坏要区别处理：前者可能意味着已确认数据受损，后者可能是不完整的尾记录。最后结合恢复日志和重启前 Put 的返回结果，判断问题发生在持久化、恢复还是请求结果认知上。”

### 90. 新副本一直不追平，如何排？

**合格**：确认新副本是否以 learner 身份加入、Leader 是否识别该成员；检查 Leader 上该副本的 `next_index`、`match_index` 是否推进，以及 AppendEntries 是否因日志冲突持续失败；必要时检查 Snapshot 发送和安装，并查看网络、磁盘错误。**加分**：对齐 Snapshot index、commit index、apply index 与 peer progress 的时间线，判断卡在复制、安装 Snapshot 还是状态机应用。**追问**：Leader 已裁剪目标日志后如何追赶？**失分**：副本进程启动就认定同步完成。**依据**：`src/storage/raft/raft_peer_progress.cpp`、`src/storage/replica/replica_snapshot_coordinator.cpp`。

**口述回答**：“新副本启动不等于数据已经追平。我会先确认它是否以 learner 身份加入，以及 Leader 是否识别到该成员；然后观察 Leader 上这个副本的复制进度，比如 `next_index` 和 `match_index` 是否在推进。如果 AppendEntries 一直失败，就检查日志冲突和回退过程；如果 Leader 已经删掉新副本缺少的旧日志，就看 Snapshot 是否成功发送、安装。最后对齐 Snapshot index、commit index 和 apply index，并检查网络、磁盘错误。只有副本完成同步并达到系统要求的状态，才能认为追平，不能只看进程已经启动。”

### 91. Topo 重启后路由短暂消失，是否一定数据丢了？

**合格**：说明路由是控制面的寻址信息，实际数据保存在 Storage 副本中并由 Raft、WAL、Snapshot 管理；`ROUTE_NOT_FOUND` 说明当前路由不可用，不能据此断定数据丢失，也不等同 `KEY_NOT_FOUND`。排查 Topo 元数据恢复、Storage 心跳和 route reconcile。**加分**：检查 Storage/Raft 副本状态，并判断 SDK 缓存的旧路由是否仍指向在线且可服务的 Leader。**追问**：缓存路由还能使用时有什么条件？**失分**：把路由缺失直接等同数据损坏或键不存在。**依据**：`src/topo/persist/topo_persist_engine.cpp`、`src/topo/service/route_service.cpp`。

**口述回答**：“Topo 重启后路由短暂消失，不代表数据一定丢了。路由是控制面的寻址信息，Storage 中的副本才保存实际数据，Raft、WAL 和 Snapshot 负责数据复制和恢复。所以 `ROUTE_NOT_FOUND` 首先说明当前没有可用路由，不能直接等同于 `KEY_NOT_FOUND` 或数据损坏。我会分别检查 Storage 副本和 Raft 状态、Topo 持久化元数据是否恢复、Storage 心跳是否重新上报，以及 route reconcile 是否完成。如果 SDK 缓存里还有旧路由，也要确认副本在线且旧地址仍是可用 Leader。定位清楚前，我会把问题描述为路由暂不可用，而不是数据已经丢失。”

### 92. 压测时 p99 突然恶化，平均 QPS 却没变？

**合格**：查尾部事件：Snapshot、fsync 抖动、Leader 切换、锁竞争、路由刷新或请求重试。**加分**：把每次异常与 metrics/日志时间戳关联，并按 workload 和 shard/replica 参数复现。**追问**：如何证明是 fsync 还是锁竞争？**失分**：只增加线程数。**依据**：`src/common/metrics/`、`scripts/bench_metrics.sh`。

### 93. 相同 request ID 的两次写内容不同会怎样？

**合格**：这是幂等键冲突，不能默默接受第二个不同写；需从服务端记录和返回码定位。**加分**：解释为什么 request payload hash 与 Snapshot 恢复一致性重要。**追问**：重启后如何检测这类冲突？**失分**：把 ID 当普通 trace ID。**依据**：`src/storage/replica/replica_loop.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`test/storage/replica/replica_test.cpp`。

### 94. 自动验证入口失败，怎样快速分类？

**合格**：先看退出阶段：CMake/依赖、端口启动、E2E 客户端返回码、关键输出缺失；查看 `BUILD_DIR/e2e_test/logs`。**加分**：确认脚本只清理自己的 E2E 数据和进程，保留失败日志；复现时固定 BUILD_DIR/GENERATOR。**追问**：如何保留失败现场同时保证进程清理？**失分**：把任何失败都说成代码逻辑问题。**依据**：`scripts/verify_project.py`、`scripts/internal/local_cluster.py`。

## J. 模拟面试顺序与复盘标准

**15 分钟快问**：1 → 4 → 5 → 7 → 21 → 40 → 53 → 65。目标是每题 90 秒内先给结论、再给一条代码证据；总分至少 24/32，且 21 与 40 不得低于 2 分。

每次复盘只记三列：**没讲出的关键事实、讲错的保证、无法定位的代码/测试**。优先修正“讲错的保证”；熟记术语但无法解释故障路径时，回到[项目速读](项目速读.md)重走一次请求链路。

## K. 十道核心题的完整答题示范

以下答案是口述范例。面试时先给结论，再按面试官兴趣展开，不要一次背完。

### K1. Q4：一次 Put 究竟什么时候成功？

可以从客户端往下画五步。第一步，SDK 根据表路由快照和稳定哈希找到 shard 的 Leader。第二步，Storage RPC handler 根据 replica ID 找到 Replica。第三步，Replica 把带 `request_id` 的写交给 Raft 提议；持久化层在日志写入路径处理 WAL。第四步，Leader 收到有效多数派响应后推进 commit index，并唤醒该 Put 的等待者。第五步，调用方得到明确 OK，才把这次逻辑写当作成功。状态机的 Map 更新和 request record 由后台 Applier 随后完成；Get 会先追到安全的 apply 位置再读取。

重点是四个位置不能混同：**请求发出、本地 WAL 写入、多数派提交、状态机应用**。本地写入只能证明这个节点接收了日志；少数派下写可能长期未提交并被后续 Leader 覆盖。超时还可能发生在服务端已提交但响应未送达之后；若出现 `RPC_ERROR` 或 `NOT_YET_COMMIT` 且 SDK 最终无法确认写入，就返回 UNKNOWN，而不是“没写入”。复盘代码：`src/sdk/client.cpp` → `src/storage/handler/storage_service_impl.cpp` → `src/storage/replica/replica_loop.cpp` → `src/storage/raft/core/`。

### K2. Q5/Q46：为什么读取要确认当前任期和多数派？

只检查本地 `is_leader` 不够：网络分区里的旧 Leader 可能尚未得知新 term。项目在构建读请求时要求当前任期已有已提交 entry，然后发送复制/心跳消息确认多数派对该 Leader 的认知，取得 read index；Replica 在状态机 apply 到该位置后才读 Map。这样多数派不可达时宁可返回错误，也不把旧值伪装成线性一致读。

追问时要解释“当前任期 entry”：新 Leader 刚当选时，对前任期日志的提交认知可能不完整；提交一条本任期 no-op 后，前面的安全前缀也能推进。项目的实现见 `src/storage/raft/core/raft_core_read.cpp` 与 `src/storage/replica/replica_read_index_checker.cpp`。这里讨论的是项目的 Leader 读路径，不包括未实现的 follower 陈旧读 API。

### K3. Q21：UNKNOWN 后业务应该怎么做？

先准确翻译：UNKNOWN 是**本次逻辑写是否提交无法确认**。例如 Leader 已提交，回包丢失；或者只有本地日志，随后被新 Leader 覆盖。客户端必须保留原请求的 `request_id` 和 payload，预算允许时用同 ID 重试；服务端查询已提交 request record 和在途记录，识别相同写或冲突写。如果最终仍无法确认，上层根据业务采取查询、补偿或人工处理。

不能把一次普通 Get 当成普遍的“提交证明”：相同 value 可能由另一写产生，原值也可能被后续写覆盖。更不能换一个 ID 直接重试非幂等副作用。对应 `src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`。

### K4. Q32：为什么副本调整用 reconcile？

建表或改副本数横跨 Catalog、Topo、多个 Storage 和 Raft 成员变更。任何 RPC、进程或网络都可能在中间失败，单个同步请求无法安全等到全部动作完成。系统先持久化“想要什么”，后台反复观察“现在是什么”，一次只推进可安全执行的下一步。上层通过表状态看进度，Topo 依据节点与副本状态决定下一轮动作。

这要求操作幂等、状态转换可恢复、失败原因可观察；代价是 DDL 返回与数据就绪之间有时间差。要对面试官强调：`create_table` 返回 OK 代表 DDL 已被接纳，不代表所有副本已完成、路由已可写。阅读 `src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp`、`src/topo/reconcile/`。

### K5. Q40/Q41：日志“复制了”为什么还可能不安全？

Raft 的 `log index` 表示位置；`commit index` 表示可安全认定的已提交前缀；`apply index` 表示状态机已执行到哪里。新 Leader 可能携带前任期日志，不能仅凭自己观察到旧日志在多数派存在就直接推进提交，因为成员与选举交错会出现 Figure 8 类反例。提交当前任期条目后，才可以安全推进相关前缀。

所以回答“写成功”不能只说“Follower 收到了”；还要问当前 term、voter 配置、多数派以及 apply。仓库有 Figure8 用例：`test/storage/raft/core/raft_cluster_test.cpp`，读前条件在 `src/storage/raft/core/raft_core_read.cpp`。

### K6. Q42：PreVote 的价值与代价

旧 Leader 与多数派隔离后可能不断发起新选举、提高 term；恢复连接时高 term 会迫使健康 Leader 退位，造成业务抖动。PreVote 在真正增加 term 前先征询“如果选举，我能否获多数派支持”，并考虑日志新旧和近期 Leader 活跃状态。多数派不同意时，隔离节点不应凭自己超时就扰乱健康集群。

它多一次消息往返，可能增加真正无 Leader 时的选举时间；它也不替代正式投票与日志安全检查。面试官若问效果，不要承诺零切主时间：项目有相关 Raft 用例，故障实验仍观察到业务失败/UNKNOWN。看 `src/storage/raft/core/raft_core_election.cpp` 与 `docs/v0.1.0/retry.md`。

### K7. Q54/Q56：为什么 Snapshot 不能只存 Map？

Map 只是业务值。要正确恢复，还需要知道这些值对应哪个 apply index/term、当时的成员信息及已处理的 request ID。否则重启后虽然读到旧值，却可能再次执行已经提交过的逻辑写。生成 Snapshot 时这些部分要来自同一应用边界；落盘后再安全处理被它覆盖的 WAL 前缀。

恢复时也不能见到损坏就随意丢数据。未提交的部分尾记录与已提交日志损坏有不同风险：前者可按恢复规则截断；后者需要标记并向其他副本追赶或暴露故障。看 `src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp` 以及 WAL 崩溃注入测试。

### K8. Q65/Q69：怎么讲性能和故障数字才可信？

先把环境说全：v0.1.0 报告是在 M3 Pro 上以单机多进程测量，默认 16 线程、2 shard、3 replica、128 字节 value、30,000 请求。Put 约 9,800 success QPS 是该负载下的历史结果；本次本机没有重跑 benchmark。它可以证明测试方法和当时表现，不能预测跨机网络、不同键分布或生产容量。

故障结果也要给分母和时间窗口。历史报告在特定写负载下，增加重试次数降低了业务可见失败/UNKNOWN，但没有达到零失败。分析原因时应拆开 Raft 选举、Topo 发布、SDK 刷新、重试预算与尾延迟。面试官更看重你会不会解释测量口径，而不是记住最高 QPS。看 `docs/v0.1.0/benchmark/` 与 `docs/v0.1.0/retry.md`。

### K9. Q73/Q76：推荐架构如何从这个项目延伸？

先问清数据是什么：用户实时特征、模型配置、实验规则、候选召回索引的读写模型完全不同。RaftBox 的 key 路由和副本复制可用于讨论特征或状态 KV，但当前内存 Map、固定分片和单进程控制面限制了容量与生产可用性。向量近邻搜索或离线训练不属于它的功能。

若给 10 万 QPS/p99 10 ms 的目标，应先拿读写比、key/value 大小、热 key、跨机拓扑、故障余量，再对单 shard、单节点、整链路逐层测量，最后估算机器并留安全余量。不能把单机报告数直接乘机器数。这里是系统设计推演，不应写成已交付推荐平台。

### K10. Q78/Q80：怎样把一致性经验迁移到 Agent？

Agent 调用外部工具时，超时可能发生在工具已执行、结果未返回之后，与 KV 写 UNKNOWN 的问题相似。给每个逻辑动作稳定的幂等键，把输入版本、执行状态和结果持久化；重试沿用同一键。若外部工具本身不支持幂等，必须有查询、补偿、审批等业务策略，不能由存储层许诺 exactly-once。

长任务还要保存阶段边界，worker 崩溃后先恢复已确认的步骤，再继续下一步；多个 worker 同时恢复同一任务时需所有权/租约与版本控制。可借鉴本项目 request ID 与 reconcile 思路，但当前仓库没有 Agent 框架接入、任务表或工具执行器。
