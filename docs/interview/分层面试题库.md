# AdvisKV 分层面试题库与评分标准

> 先读[项目速读](项目速读.md)和[证据与边界](证据与边界.md)。题库按项目主线、基础原理、故障排查、岗位设计题组织。每题的“合格”是至少应说出的事实，“加分”是能经受追问的因果与取舍，“失分”列出常见错误。代码入口用于复盘，不代表该场景在本次全部复测。标有“设计推演”的题目不属于当前已实现功能。

## 使用方法与统一评分

每题 0–4 分：**0** 没有回答或核心结论相反；**1** 只说术语，不能讲流程；**2** 说清“合格”要点；**3** 再说清“加分”中的一个边界、取舍或故障；**4** 能结合代码/测试定位并解释追问。含错误保证（例如把 `UNKNOWN` 说成一定没写入）时最高 1 分。系统设计题的 4 分还要有量化目标、演进和验证方案。先独立回答 90 秒，再看标准；项目题应能打开对应源码给面试官解释。

## A. 先讲清项目（1–8）

### 1. 用 30 秒介绍 AdvisKV
**合格**：C++17 分布式 KV；Catalog 管 DDL、Topo 管副本和路由、Storage 用 Raft/WAL/Snapshot，SDK 路由请求。**加分**：给出三副本本地 E2E 证据与单进程控制面、固定 shard 等边界。**追问**：一次 Put 经过哪些模块？**失分**：声称生产部署或 AI 功能已完成。**依据**：`README.md`、`scripts/verify_project.py`。

### 2. Catalog、Topo、Storage 为什么拆开？
**合格**：分别承担库表元数据/DDL、期望副本与路由、实际数据复制。**加分**：说明控制面异步收敛和数据面高频读写的节奏不同；Catalog/Topo 当前单进程是可用性短板。**追问**：Topo 故障时已有路由能否继续访问？需按 SDK 缓存和路由过期条件回答。**失分**：说三个模块都通过 Raft 高可用。**依据**：`src/catalog/`、`src/topo/`、`src/storage/`。

### 3. 一次建表何时算完成？
**合格**：Catalog 持久化 ADDING，Topo 建目标副本，Storage 执行创建，表与可写路由满足条件后进入就绪。**加分**：区分 DDL RPC 的 OK 与最终 NORMAL；Topo 不可达可由 reconciler 后续重试。**追问**：启动时没有足够健康节点怎么办？**失分**：把“请求返回 OK”当“已可读写”。**依据**：`src/catalog/service/ddl_service.cpp`、`src/topo/service/table_service.cpp`。

### 4. 一次 Put 的完整路径是什么？
**合格**：SDK 查路由 → Leader RPC → Replica 提议 Raft 日志 → 多数派提交 → apply 到状态机；日志由持久化层处理。**加分**：说明在路径中超时可能产生未知结果，同一逻辑请求沿用 `request_id`。**追问**：本地日志写入后但未多数派确认能否回 OK？**失分**：将 WAL 写入等同多数派提交。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica.cpp`、`src/storage/raft/core/`。

### 5. 一次 Get 为什么没有直接读 Map？
**合格**：确认自己仍是 Leader、取得 read index、apply 至该位置再读取。**加分**：解释新 Leader 当前任期 no-op 提交和多数派确认，指出多数派不可达时读可能失败。**追问**：如果允许陈旧读如何设计独立 API？**失分**：只看 `is_leader` 就声称线性一致。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

### 6. 当前项目最强的工程证据是什么？
**合格**：最小三副本 E2E 本机通过；仓库有单测、故障 E2E、benchmark 报告。**加分**：区分本次抽验与未重跑的测试，讲出可重复命令。**追问**：历史数字的机器和工作负载？**失分**：说 256 项本机全通过，或将历史 benchmark 说成今天新测。**依据**：`scripts/verify_project.py`、`docs/v0.1.0/benchmark/`。

### 7. 项目的最大限制是什么？
**合格**：运行时 Map 引擎，固定 shard 数，Catalog/Topo 单进程；`request_id` 无 TTL。**加分**：按业务影响排序：大数据量、热点与扩容、控制面故障、记录增长。**追问**：先改哪个、如何验收？**失分**：只说“还要优化性能”。**依据**：`README.md`、`docs/版本.md`。

### 8. 如果面试官问你究竟做了什么？
**合格**：按个人真实工作选一条链路，讲背景、方案、取舍、问题、结果，并打开对应代码/测试。**加分**：明确个人与团队边界、哪些结果是历史报告。**追问**：最难的 bug 如何复现？**失分**：把整个仓库每项功能都说成个人独立完成，却无法解释。**依据**：[七个故事](证据与边界.md)。

## B. C++、并发与工程基础（9–18）

### 9. SDK 路由快照如何避免读写竞争？
**合格**：构造新的不可变 TableRouteSnapshot，使用 shared_ptr 原子 load/store 发布，读线程获取稳定快照。**加分**：说明读侧不会看到“更新一半的路由”，但缓存仍可能过期，需错误驱动刷新。**追问**：shared_ptr 原子操作的成本？**失分**：把线程安全等同业务路由实时正确。**依据**：`src/sdk/route_cache.cpp`。

### 10. Replica 为什么需要多个锁和任务队列？
**合格**：Raft Core、状态机、持久化快照等状态有不同并发访问路径；ReplicaLoop 将事件串行处理。**加分**：能指出锁顺序、长时间 RPC 持锁和回调重入的风险，并用线程竞态测试验证。**追问**：如何排查死锁？**失分**：称“用了 mutex 就没有并发问题”。**依据**：`src/storage/replica/replica.cpp`、`src/storage/replica/replica_loop.cpp`。

### 11. `std::atomic` 与 mutex 如何选择？
**合格**：单个独立状态可用原子，多个字段需保持不变量时需要锁或不可变快照。**加分**：用路由快照和 Raft Core 状态举例；解释内存可见性与互斥并非同一问题。**追问**：`memory_order_relaxed` 适合什么？**失分**：认为所有共享变量换成 atomic 即可。**依据**：`src/sdk/route_cache.cpp`、`src/sdk/client.cpp` 的 request ID 序号。

### 12. C++ 对象生命周期在异步任务中有什么风险？
**合格**：后台任务持有指针，销毁前要停止任务并等待退出。**加分**：指出 `RouteCache::~RouteCache` 调用 stop，Replica 关闭顺序需保证回调不访问已销毁成员。**追问**：shared_ptr 是否能替代所有生命周期管理？**失分**：忽略悬空回调。**依据**：`src/sdk/route_cache.cpp`、`src/storage/replica/replica.cpp`。

### 13. 如何判断一个 Raft 并发 bug 可复现？
**合格**：固定初始拓扑、操作序列、定时/分区条件，记录 term、index、成员、消息时序。**加分**：用模拟集群用例或故障注入替代随机睡眠，运行 ThreadSanitizer/ASan 作为补充。**追问**：偶现失败如何缩小事件序列？**失分**：只靠加长 sleep。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`scripts/asan/`。

### 14. `request_id` 的生成与碰撞风险？
**合格**：SDK 用进程实例随机值加原子递增序号生成默认 ID；调用方也可显式传 ID。**加分**：说明碰撞概率不是数学上的零，跨重启调用方若要重试原请求须保存原 ID；服务端还校验相同 ID 的请求内容。**追问**：跨地域业务 ID 如何设计？**失分**：超时重试重新生成 ID。**依据**：`src/sdk/client.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 15. 为什么要把 RPC 总超时和单次 RPC 超时分开？
**合格**：整个逻辑请求有 deadline，每次 RPC 只使用剩余预算与配置上限的较小值。**加分**：还需给路由刷新、退避留时间；重试次数与时间预算同时限制。**追问**：线程被调度延迟时该如何更新预算？**失分**：每次重试都给完整总超时。**依据**：`src/sdk/client.cpp`。

### 16. RAII 在本项目中解决什么？
**合格**：资源或清理动作绑定作用域，异常/提前返回仍执行；可举 Result guard、锁、进程 `finally` 的同类思想。**加分**：解释 C++ 析构不能抛异常、关闭动作与对象所有权要清晰。**追问**：`Defer` 捕获局部引用的生命周期？**失分**：把 RAII 仅理解为智能指针。**依据**：`src/common/defer.h`、`src/sdk/client.cpp`。

### 17. 如何避免哈希分片在进程间不一致？
**合格**：用项目固定的 stable hash 算法，而非依赖实现细节的进程内哈希；基于相同 shard_count 计算。**加分**：指出 shard_count 变化会大规模重映射，因此现版本固定分片数；升级哈希算法需要兼容策略。**追问**：如何设计 split 迁移？**失分**：直接用随机种子的 `std::hash` 做持久路由。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`。

### 18. 编译与运行依赖如何复现？
**合格**：vcpkg 子模块、`setup.sh` 安装依赖、CMake 构建、Python 验证入口。**加分**：说明 build tree 的 generator 要一致；本机 `build-make` 使用 Unix Makefiles，默认 `build` 走 Ninja。**追问**：在干净 CI 上怎么判断失败是依赖、编译还是运行？**失分**：只给本机绝对路径。**依据**：`CMakeLists.txt`、`scripts/setup.sh`、`scripts/build.sh`。

## C. RPC、SDK 与结果语义（19–28）

### 19. 路由缓存冷启动时怎么处理？
**合格**：缓存 miss 时主动从 Topo 拉取整表路由，再按 key 找 shard。**加分**：失败时按状态返回，不能无路由地盲发 Storage；后台定期刷新与请求路径刷新并存。**追问**：Topo 暂时不可用而缓存已有路由时怎样？**失分**：每次都必定请求 Topo。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`。

### 20. 哪些错误触发刷新路由？
**合格**：如 NOT_LEADER、REPLICA_NOT_FOUND、ROUTE_NOT_FOUND、IS_RECOVERING、RPC_ERROR；其他可重试错误不一定刷新。**加分**：解释 `NOT_YET_COMMIT` 与 `READ_INDEX_NOT_READY` 更像等待状态，盲目刷新路由可能浪费预算。**追问**：为什么设置独立 route_max_retries？**失分**：所有错误无限刷新。**依据**：`src/sdk/client.cpp` 中 `classify_error`。

### 21. 写超时后 `UNKNOWN` 的含义？
**合格**：服务器可能提交，也可能未提交；客户端在预算内无法确认，不能当成失败重新生成 ID。**加分**：用同一 `request_id` 重试；Get 只是应用层检查，不总能还原该写是否曾发生。**追问**：如果覆盖写之后又有别人的写，Get 有什么歧义？**失分**：说 UNKNOWN 一定没写入。**依据**：`src/sdk/client.cpp` 中 `finalize_status`。

### 22. 幂等写如何落地？
**合格**：同一 request ID 与操作内容关联，重复 Put/Delete 不重复执行；记录进入状态机并写入 Snapshot。**加分**：指出同 ID 不同 payload 应拒绝、记录没有 TTL 的内存增长边界。**追问**：客户端重启后如何保留逻辑请求 ID？**失分**：只在 SDK 进程内缓存 ID。**依据**：`src/storage/replica/replica_loop.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`test/storage/replica/replica_test.cpp`。

### 23. RPC 返回 OK 就代表业务成功吗？
**合格**：gRPC 传输状态与业务 Status 分开看；服务端 handler 可用 gRPC OK 承载业务错误码。**加分**：解释 SDK 依据业务错误决定刷新路由/重试；日志、metrics 应同时记录两层结果。**追问**：超时但服务端已提交怎么办？**失分**：只检查 `grpc::Status::OK`。**依据**：`src/storage/handler/storage_service_impl.cpp`、`src/sdk/storage_client.cpp`。

### 24. 为什么重试可能放大负载？
**合格**：故障期间多个客户端同步重试会增加 Topo 和 Leader 压力。**加分**：项目已有重试次数、总预算与指数退避；生产化可增加 jitter、限流和熔断，并按成功率/尾延迟验收。**追问**：如何避免雪崩？**失分**：认为重试次数越多越好。**依据**：`src/sdk/client.cpp`；后续策略为设计推演。

### 25. 读失败如何映射给调用方？
**合格**：READ_INDEX_NOT_READY 表示当前任期读条件未满足；SDK 最终会将其映射为稍后再试。**加分**：与写 UNKNOWN 区分：读失败不会产生写入结果不确定性。**追问**：如果调用方需要弱一致读怎么办？**失分**：将读失败返回空值。**依据**：`src/sdk/client.cpp`。

### 26. 如何给 SDK 定义可观察指标？
**合格**：逻辑请求数、成功/失败、UNKNOWN、路由命中/刷新、Storage RPC 延迟。**加分**：区分逻辑请求与重试 attempt，按错误码和 percentile 排查；项目已有部分 metrics。**追问**：如何量化切主窗口？**失分**：只看平均 QPS。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`docs/v0.1.0/retry.md`。

### 27. 如果客户端持有旧 table_id，会怎样？
**合格**：删表重建后 table_id 改变，旧路由不能当作新表数据；需刷新路由，按实际业务状态处理旧副本错误。**加分**：说明 E2E 验证了删表重建后旧 key 不可见。**追问**：怎样做表代际版本防 ABA？**失分**：仅以同名表判断是同一张表。**依据**：`src/sdk/route_cache.cpp`、`test/e2e/test_basic_chain.py`。

### 28. 什么场景下客户端不该自动重试？
**合格**：参数错误、确定的业务错误，或重试预算耗尽时停止；写操作如无法确认应暴露 UNKNOWN。**加分**：明确业务层外部副作用不能依赖普通 RPC 重试，需要业务幂等键。**追问**：Delete 不存在键的业务语义是什么？**失分**：所有失败都自动无限重试。**依据**：`src/sdk/client.cpp`；外部副作用为设计推演。

## D. 分片、Topo 与副本控制（29–38）

### 29. key 如何定位到 shard？
**合格**：SDK 对 key 做 stable hash，以建表时 shard_count 求 shard index，再取该 shard 的路由。**加分**：解释相同算法与表 ID/分片数的一致性、分片数固定的后果。**追问**：如何应对热点 key？**失分**：把“多 shard”直接说成自动均衡热点。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`。

### 30. Topo 为什么只发布一个可写 Leader？
**合格**：写请求必须有明确 Leader；RouteService 校验可写路由中恰有一个 Leader。**加分**：在竞选或 Leader 状态冲突时暂不发布，优先保证路由安全，代价是短暂不可用。**追问**：多个不同 term Leader 上报怎么办？**失分**：随机选一个。**依据**：`src/topo/service/route_service.cpp`、`test/topo/service/route_reconcile_service_test.cpp`。

### 31. 节点心跳承担什么职责？
**合格**：Storage NodeAgent 向 Topo 注册并报告状态，Topo 用于节点健康与副本计划，Storage 接收期望副本动作。**加分**：区分“心跳丢失”与“节点永久坏”；阈值过短可能误替换。**追问**：网络分区时两个侧面的视图为何不同？**失分**：心跳正常就能证明数据已提交。**依据**：`src/storage/node_agent/node_agent.cpp`、`src/topo/service/node_service.cpp`。

### 32. 期望状态和实际状态为什么分开？
**合格**：期望状态表达目标副本数/位置，实际状态反映心跳和 Raft 成员；reconciler 多轮推进。**加分**：可解释重试幂等与中间态，让控制面重启后继续收敛。**追问**：计划与实际永远不一致时怎样报警？**失分**：一次修改元数据就认为复制完成。**依据**：`src/topo/reconcile/`、`src/topo/service/table_service.cpp`。

### 33. 在线扩容副本一般为什么先加 learner？
**合格**：新副本先复制现有日志/快照，不立即计入写入多数派，再升为 voter。**加分**：说明直接提升未追平节点会影响提交、故障恢复和配置安全。**追问**：快照传输期间日志又增长怎么办？**失分**：把新节点一创建就算健康 voter。**依据**：`src/storage/raft/raft_membership.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 34. 缩容到零意味着什么？
**合格**：表可以有零副本的目标状态，但没有可用 KV 路由，读写不可进行；后续可再扩容。**加分**：说明控制面的表就绪与数据面的可访问性应分开定义。**追问**：零副本后原数据如何处理、扩回后是否还存在？必须按具体测试和语义回答。**失分**：说零副本仍可读。**依据**：`test/e2e/test_basic_chain.py` 的 scale-to-zero 用例、`src/topo/service/table_service.cpp`。

### 35. 副本选择如何避免同故障域？
**合格**：选择器优先健康节点，排除同 shard 已用节点，尝试不同 DC 并平衡负载。**加分**：指出同机多进程测试不等于真实跨故障域容灾，DC 标签只有部署正确才有意义。**追问**：可用 DC 数不足怎么办？**失分**：标签不同就声称物理机故障隔离。**依据**：`src/topo/selector/node_selector/node_selector.cpp`、相应测试。

### 36. 新 Leader 出现后路由多久更新？
**合格**：Storage 心跳上报状态，Topo 的后台路由 reconcile 依据观察到的 Leader 发布，SDK 再定期或按错误刷新。**加分**：说出这是多阶段传播，切主时间包括选举、上报、路由、客户端重试。**追问**：怎样测业务恢复窗口？**失分**：把 Raft 选举时间直接当业务恢复时间。**依据**：`src/topo/background/background.cpp`、`src/sdk/route_cache.cpp`、`scripts/failover_bench.sh`。

### 37. 控制面故障会影响哪些操作？
**合格**：新 DDL、路由刷新、节点调度会受影响；已有 SDK 缓存与 Storage 数据面在一定条件下可能继续工作。**加分**：按“现有路由是否仍有效、Leader 是否变化”分情形，不给绝对可用保证。**追问**：如何给 Catalog/Topo 做高可用？**失分**：称控制面故障对业务完全无影响。**依据**：`src/sdk/route_cache.cpp`、`README.md`。

### 38. 如何设计在线 shard split？【设计推演】
**合格**：需要版本化路由、数据迁移、双写或冻结窗口、原子切换与回滚规则。**加分**：定义迁移期间读写一致性、热点和后台速率限制、老 SDK 兼容，给出迁移完成证据。**追问**：split 时旧 key 的定位如何保持一致？**失分**：直接修改 shard_count 后对全部 key 取模。**依据**：当前限制见 `README.md`；现有哈希路由在 `src/sdk/route_cache.cpp`。

## E. Raft、一致性与成员变更（39–52）

### 39. Raft 选主保证了什么？
**合格**：同一任期选举依赖多数派和日志新旧约束，Leader 获得复制权。**加分**：指出网络延迟可能有旧 Leader 自认 Leader，写入仍需多数派提交，读需 ReadIndex 确认。**追问**：少数派能否选出可提交 Leader？**失分**：认为任意节点可单独继续写。**依据**：`src/storage/raft/core/raft_core_election.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 40. term、log index、commit index、apply index 分别是什么？
**合格**：term 是选举时代，index 是日志位置，commit 是多数派确认的安全前缀，apply 是已执行到状态机的位置。**加分**：解释通常 apply ≤ commit，日志存在不等于已提交，读前需追至 read index。**追问**：崩溃重启如何恢复这些状态？**失分**：把 append、commit、apply 混为一谈。**依据**：`src/storage/raft/core/`、`src/storage/replica/replica_applier.cpp`。

### 41. 为什么旧任期日志不能只凭多数派复制直接提交？
**合格**：Raft 对旧任期条目直接推断提交有 Figure 8 风险；Leader 需提交当前任期条目，再安全带上此前前缀。**加分**：联系新 Leader no-op 与 ReadIndex 前置条件。**追问**：当前任期 no-op 的作用？**失分**：所有多数派已有条目都可立即宣布提交。**依据**：`test/storage/raft/core/raft_cluster_test.cpp` 的 Figure8 用例、`src/storage/raft/core/raft_core_read.cpp`。

### 42. PreVote 解决什么，又不解决什么？
**合格**：选举前预探多数派，旧隔离节点不轻易抬高 term 干扰健康 Leader。**加分**：说明仍需正式选举、日志新旧比较和多数派；PreVote 不解决控制面单点。**追问**：PreVote 接收者会增加 term 吗？**失分**：把 PreVote 当已获得 Leader 身份。**依据**：`src/storage/raft/core/raft_core_election.cpp`、PreVote 用例。

### 43. 日志冲突如何修复？
**合格**：Follower 检查 prev index/term，不匹配拒绝；Leader 回退进度并补发一致前缀，必要时快照追赶。**加分**：指出未提交旧 Leader 日志可被新 Leader 覆盖，已提交前缀必须保留。**追问**：Follower 落后到被压缩日志之前怎么办？**失分**：简单追加到尾部。**依据**：`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_peer_progress.cpp`。

### 44. 多数派提交为什么是 N/2+1？
**合格**：任意两个多数派有交集，防止两个互不相交的提交历史。**加分**：分别说明 1、3、5 副本可容忍的故障数与成本，解释增加偶数副本未必增加容错数。**追问**：跨 DC 延迟如何影响写 p99？**失分**：只按“有几个副本响应”不考虑配置成员身份。**依据**：`src/storage/raft/raft_membership.cpp`、Raft 集群测试。

### 45. Leader 崩溃时为什么可能返回 UNKNOWN？
**合格**：请求可能在故障前已经提交，而响应丢失；也可能只写了少数节点，随后被覆盖。**加分**：通过 request ID 去重与重试争取确认，并向业务暴露仍不确定的状态。**追问**：为什么简单 Get 不能严格判定原请求？**失分**：把超时直接映射为“回滚”。**依据**：`src/sdk/client.cpp`、`docs/v0.1.0/retry.md`。

### 46. 项目 Get 的线性一致读前提有哪些？
**合格**：本节点是 Leader、当前任期有已提交 entry、多数派确认 Leader 身份、状态机 apply 到 read index。**加分**：讨论网络分区与并发写入时线性化点的合理位置。**追问**：单副本时如何满足多数派？**失分**：只读 Leader 内存。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

### 47. ReadIndex 与 Lease Read 有什么差别？【原理与推演】
**合格**：ReadIndex 通过当次多数派确认，不依赖严格时钟租约；Lease Read 依赖租约有效性和时钟/暂停假设，通常更低延迟。**加分**：说明当前项目走 ReadIndex 路径，不宣称已有 Lease Read。**追问**：GC/进程暂停或时钟跳变如何影响租约？**失分**：把 ReadIndex 说成纯本地读。**依据**：`src/storage/replica/replica_read_index_checker.cpp`。

### 48. 成员变更时 quorum 怎么看？
**合格**：先辨清当前配置中的 voter 集合，learner 不参与提交多数派；成员变更本身也需经 Raft 日志安全生效。**加分**：说明并发配置变更需要序列化、不能跳过追赶。**追问**：3 voter 缩到 2 voter 时容错能力变化？**失分**：把 learner 也算入 quorum。**依据**：`src/storage/raft/raft_membership.cpp`、成员变更测试。

### 49. 分区后旧 Leader 恢复，如何避免它覆盖新历史？
**合格**：新 term 与日志匹配约束使旧 Leader 退位；冲突的未提交日志被新 Leader 修复。**加分**：PreVote 降低旧节点扰动，路由层也应撤下旧 Leader。**追问**：旧 Leader 期间已向客户端成功返回的写能丢吗？按多数派提交语义回答。**失分**：认为节点恢复时本地日志永远优先。**依据**：`src/storage/raft/core/raft_core_election.cpp`、Raft Cluster 故障测试。

### 50. 同一 shard 出现两个 Leader 上报怎么办？
**合格**：比较任期和成员状态；路由服务不会无条件给客户端两个可写 Leader，不确定时清除路由。**加分**：区分“上报视图存在冲突”与 Raft 安全性真的被破坏；需抓 term、日志与心跳时序。**追问**：高 term Leader 未获多数派时可写吗？**失分**：Topo 任选端点直接放行。**依据**：`src/topo/service/route_service.cpp`、RouteServiceReconcile 测试。

### 51. Raft 正确性如何测试？
**合格**：选主、复制、少数派无法提交、Leader 崩溃、冲突覆盖、落后追赶、Snapshot 和并发提议。**加分**：说明单元模拟与真实多进程 E2E 覆盖的层次不同；Maelstrom 是额外故障注入入口。**追问**：如何验证线性一致历史？**失分**：只测 Put 后立即 Get。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`tools/maelstrom_raft/`。

### 52. 为什么 Raft 不自动解决所有数据一致性问题？
**合格**：Raft 管复制日志顺序与提交，业务还需正确的请求去重、状态机确定性、读路径、跨 shard 语义。**加分**：指出本项目不提供跨 shard 事务或动态 rebalance。**追问**：两个 shard 的原子更新如何做？**失分**：只要用了 Raft 就是全局事务。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`README.md`。

## F. WAL、Snapshot 与恢复（53–62）

### 53. WAL 为什么要在应用状态机前持久化？
**合格**：重启后可以依据日志重建尚未进入 Snapshot 的状态，Raft 承诺不能只存在内存。**加分**：区分本地持久化、复制多数派和状态机 apply 三个完成点。**追问**：fsync 失败应怎么办？**失分**：只要写入 page cache 就等于所有故障模型下持久。**依据**：`src/storage/persist/persist_engine.cpp`、`src/storage/replica/replica_applier.cpp`。

### 54. Snapshot 里要放哪些内容？
**合格**：KV、状态机 apply index/term、请求去重记录，以及恢复 Raft 成员所需元数据。**加分**：说明缺少 request record 会使重启后的重复写可能再次执行。**追问**：Snapshot 与 WAL 裁剪顺序如何保证安全？**失分**：只把 Map 键值序列化。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp`。

### 55. 为什么需要 WAL 截断与快照边界？
**合格**：Snapshot 覆盖以前的日志，保留后续日志便于恢复与追赶；边界不连续会产生缺口。**加分**：崩溃发生在写 Snapshot、替换文件、裁剪 WAL 的不同阶段，恢复需验证完整性。**追问**：先删 WAL 再写 Snapshot 会怎样？**失分**：只按文件大小轮转不看 index。**依据**：`src/storage/persist/persist_engine.cpp`、PersistEngine 测试。

### 56. WAL 尾部损坏如何区分处理？
**合格**：读取记录长度/CRC，未提交损坏尾部可截断；已提交部分损坏需谨慎，可能进入追赶恢复。**加分**：解释为何不能静默丢掉已提交数据。**追问**：如果多数派都损坏该怎么办？应说明当前方案边界。**失分**：遇到 CRC 错误直接清空全部数据。**依据**：`src/storage/persist/persist_engine.cpp`、`test/storage/persist/wal_crash_injection_test.cpp`。

### 57. 落后副本何时走日志追赶，何时走 Snapshot？
**合格**：Leader 仍持有目标日志时发 AppendEntries；所需日志已被压缩时安装 Snapshot，再补后续日志。**加分**：考虑安装过程中 Leader 继续写入，目标副本需追赶到最新提交位置后才能安全升 voter。**追问**：Snapshot 分片接收中断怎样续传或重试？**失分**：快照安装完成就直接假定最新。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`test/e2e/test_basic_chain.py`。

### 58. 为什么说当前是“内存引擎但支持持久化”？
**合格**：运行时读写由 Map 完成，WAL/Snapshot 保存可恢复状态；重启要加载到内存。**加分**：解释这与 RocksDB/LSM 的点查、压缩、写放大和容量模型不同。**追问**：数据超过内存怎么办？**失分**：称 Map 完全不落盘，或称已实现磁盘 KV 引擎。**依据**：`src/storage/engine/map_engine.cpp`、`src/storage/persist/persist_engine.cpp`。

### 59. Snapshot 生成时并发写如何保证一致视图？
**合格**：必须在确定的 apply index 捕获 KV 与去重记录的同一逻辑状态，并正确协调锁与持久化顺序。**加分**：定位 ReplicaSnapshotCoordinator 和 KvStateMachine 的捕获路径，说明长时间持锁的尾延迟风险。**追问**：怎样改为增量快照？**失分**：边遍历 Map 边无锁写文件却声称一致。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 60. 为什么恢复期间拒绝读写？
**合格**：本地状态可能落后于应有的提交位置，不应给客户端错误的成功读写；返回 IS_RECOVERING。**加分**：说明恢复完成判据与路由摘除需要协同。**追问**：如果只有一个健康副本怎样处理可用性？**失分**：Map 加载完成就立即对外宣称最新。**依据**：`src/storage/replica/replica.cpp`、`src/storage/raft/core/raft_core_recovery.cpp`。

### 61. 如何验证重启恢复？
**合格**：写入数据，停服务，重启后读回；还要检查 Raft term/index、成员及 request ID 记录。**加分**：覆盖不同崩溃点、部分 WAL 记录、快照与后续 WAL 同时存在。**追问**：如何证明幂等在重启后仍生效？**失分**：只看进程成功启动。**依据**：`test/storage/persist/persist_engine_test.cpp`、`test/e2e/test_basic_chain.py`。

### 62. 如果改用 RocksDB，你会先改什么？【设计推演】
**合格**：定义 KVEngine 接口与持久化职责边界，明确 Raft WAL 和引擎 WAL 是否重复、Snapshot/恢复如何映射。**加分**：给出迁移兼容、批量写入、性能/容量与崩溃测试计划。**追问**：如何避免同一条写在两个日志之间失配？**失分**：只替换 `MapEngine` 类名。**依据**：当前接口 `src/storage/engine/kv_engine.h`，限制见 `README.md`。

## G. 测试、性能与部署（63–72）

## H. 推荐架构、AI/Agent 与系统设计（73–84，均为设计推演）

### 73. 如果把这个 KV 用于推荐系统，存什么、不存什么？

### 74. 用户特征按 user_id 分片会遇到什么？
**合格**：用户访问和写入分布不均造成热点；单个大用户无法靠 hash 自动拆分。**加分**：先测 top key 与 shard 负载，考虑特征拆 key、缓存、多级聚合或业务分桶，并说明一致性成本。**追问**：迁移分桶规则如何兼容旧读？**失分**：只增加副本数就说写热点解决。**依据**：现有哈希路由 `src/common/stable_hash.h`；其余为推演。

### 75. 推荐链路的配置数据要强一致吗？

## I. 故障排查题（85–94）

### 85. `wait_table` 一直不成功，先查什么？
**合格**：Catalog 表状态与错误、Topo 目标规格、健康 Storage 数、Raft Leader、路由是否可写。**加分**：按建表流程定位卡在节点选择、创建副本、成员变更还是路由发布；看对应服务日志。**追问**：如何从日志区分节点不足与 Leader 未选出？**失分**：只重启所有服务。**依据**：`src/topo/service/table_service.cpp`、`src/topo/service/route_service.cpp`。

### 86. Put 返回 NOT_LEADER，但 Topo 仍给旧端点，怎么办？
**合格**：SDK 刷新路由并在预算内重试；排查心跳到 Topo 的传播与路由 reconcile。**加分**：若写结果已不确定，保持 request ID；记录旧新 term 与时间线。**追问**：旧 Leader 已提交但回包丢失怎么办？**失分**：换新 ID 重试。**依据**：`src/sdk/client.cpp`、`src/topo/service/route_service.cpp`。

### 87. 三副本中一台宕机，写入突然全部超时，怎么查？
**合格**：确认实际 voter 成员和可达多数派、故障节点是否为 Leader、选举及 WAL/fsync 状态。**加分**：区分 Raft 不提交、SDK 旧路由、控制面未更新和资源饱和；对照 term/index 与 RPC metrics。**追问**：如果剩余两台其实不在同一个 voter 配置中呢？**失分**：直接认定“3 副本可容忍 1 故障所以代码一定错”。**依据**：`src/storage/raft/`、`src/sdk/client.cpp`。

### 88. Get 返回旧值，如何判断是 bug？
**合格**：先确认请求是否明确 Put 成功、读写是否同表同 key、是否经过旧路由或表重建；检查 read index 与 apply index。**加分**：如果 Put 是 UNKNOWN，不能拿它当已提交前提；收集完整并发历史验证线性化。**追问**：怎样采集足够的并发历史？**失分**：只看本地 Map 内容。**依据**：`src/storage/replica/replica.cpp`、`src/sdk/client.cpp`。

### 89. 重启后部分键丢失，怎么定位？

### 90. 新副本一直不追平，如何排？

## K. 十道核心题的完整答题示范

以下答案是口述范例。面试时先给结论，再按面试官兴趣展开，不要一次背完。

### K1. Q4：一次 Put 究竟什么时候成功？

可以从客户端往下画五步。第一步，SDK 根据表路由快照和稳定哈希找到 shard 的 Leader。第二步，Storage RPC handler 根据 replica ID 找到 Replica。第三步，Replica 把带 `request_id` 的写交给 Raft 提议；持久化层在日志写入路径处理 WAL。第四步，Leader 收到有效多数派响应后推进 commit index，Replica 将已提交日志 apply 到 Map 状态机并记录 request ID。第五步，调用方得到明确 OK，才把这次逻辑写当作成功。

重点是四个位置不能混同：**请求发出、本地 WAL 写入、多数派提交、状态机应用**。本地写入只能证明这个节点接收了日志；少数派下写可能长期未提交并被后续 Leader 覆盖。超时还可能发生在服务端已提交但响应未送达之后，因此 SDK 返回 UNKNOWN 而不是“没写入”。复盘代码：`src/sdk/client.cpp` → `src/storage/handler/storage_service_impl.cpp` → `src/storage/replica/replica.cpp` → `src/storage/raft/core/`。

### K2. Q5/Q46：为什么读取要确认当前任期和多数派？

只检查本地 `is_leader` 不够：网络分区里的旧 Leader 可能尚未得知新 term。项目在构建读请求时要求当前任期已有已提交 entry，然后发送复制/心跳消息确认多数派对该 Leader 的认知，取得 read index；Replica 在状态机 apply 到该位置后才读 Map。这样多数派不可达时宁可返回错误，也不把旧值伪装成线性一致读。

追问时要解释“当前任期 entry”：新 Leader 刚当选时，对前任期日志的提交认知可能不完整；提交一条本任期 no-op 后，前面的安全前缀也能推进。项目的实现见 `src/storage/raft/core/raft_core_read.cpp` 与 `src/storage/replica/replica_read_index_checker.cpp`。这里讨论的是项目的 Leader 读路径，不包括未实现的 follower 陈旧读 API。

### K3. Q21：UNKNOWN 后业务应该怎么做？

先准确翻译：UNKNOWN 是**本次逻辑写是否提交无法确认**。例如 Leader 已提交，回包丢失；或者只有本地日志，随后被新 Leader 覆盖。客户端必须保留原请求的 `request_id` 和 payload，预算允许时用同 ID 重试；服务端查询已提交 request record 和在途记录，识别相同写或冲突写。如果最终仍无法确认，上层根据业务采取查询、补偿或人工处理。

不能把一次普通 Get 当成普遍的“提交证明”：相同 value 可能由另一写产生，原值也可能被后续写覆盖。更不能换一个 ID 直接重试非幂等副作用。对应 `src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`。

### K4. Q32：为什么副本调整用 reconcile？

建表或改副本数横跨 Catalog、Topo、多个 Storage 和 Raft 成员变更。任何 RPC、进程或网络都可能在中间失败，单个同步请求无法安全等到全部动作完成。系统先持久化“想要什么”，后台反复观察“现在是什么”，一次只推进可安全执行的下一步。上层通过表状态看进度，Topo 依据节点与副本状态决定下一轮动作。

这要求操作幂等、状态转换可恢复、失败原因可观察；代价是 DDL 返回与数据就绪之间有时间差。要对面试官强调：`create_table` 返回 OK 代表 DDL 已被接纳，不代表所有副本已完成、路由已可写。阅读 `src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp`、`src/topo/reconcile/`。

### K5. Q40/Q41：日志“复制了”为什么还可能不安全？

Raft 的 `log index` 表示位置；`commit index` 表示可安全认定的已提交前缀；`apply index` 表示状态机已执行到哪里。新 Leader 可能携带前任期日志，不能仅凭自己观察到旧日志在多数派存在就直接推进提交，因为成员与选举交错会出现 Figure 8 类反例。提交当前任期条目后，才可以安全推进相关前缀。

所以回答“写成功”不能只说“Follower 收到了”；还要问当前 term、voter 配置、多数派以及 apply。仓库有 Figure8 用例：`test/storage/raft/core/raft_cluster_test.cpp`，读前条件在 `src/storage/raft/core/raft_core_read.cpp`。

### K6. Q42：PreVote 的价值与代价

旧 Leader 与多数派隔离后可能不断发起新选举、提高 term；恢复连接时高 term 会迫使健康 Leader 退位，造成业务抖动。PreVote 在真正增加 term 前先征询“如果选举，我能否获多数派支持”，并考虑日志新旧和近期 Leader 活跃状态。多数派不同意时，隔离节点不应凭自己超时就扰乱健康集群。

它多一次消息往返，可能增加真正无 Leader 时的选举时间；它也不替代正式投票与日志安全检查。面试官若问效果，不要承诺零切主时间：项目有相关 Raft 用例，故障实验仍观察到业务失败/UNKNOWN。看 `src/storage/raft/core/raft_core_election.cpp` 与 `docs/v0.1.0/retry.md`。

### K7. Q54/Q56：为什么 Snapshot 不能只存 Map？

Map 只是业务值。要正确恢复，还需要知道这些值对应哪个 apply index/term、当时的成员信息及已处理的 request ID。否则重启后虽然读到旧值，却可能再次执行已经提交过的逻辑写。生成 Snapshot 时这些部分要来自同一应用边界；落盘后再安全处理被它覆盖的 WAL 前缀。

恢复时也不能见到损坏就随意丢数据。未提交的部分尾记录与已提交日志损坏有不同风险：前者可按恢复规则截断；后者需要标记并向其他副本追赶或暴露故障。看 `src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp` 以及 WAL 崩溃注入测试。

### K8. Q65/Q69：怎么讲性能和故障数字才可信？

先把环境说全：v0.1.0 报告是在 M3 Pro 上以单机多进程测量，默认 16 线程、2 shard、3 replica、128 字节 value、30,000 请求。Put 约 9,800 success QPS 是该负载下的历史结果；本次本机没有重跑 benchmark。它可以证明测试方法和当时表现，不能预测跨机网络、不同键分布或生产容量。

故障结果也要给分母和时间窗口。历史报告在特定写负载下，增加重试次数降低了业务可见失败/UNKNOWN，但没有达到零失败。分析原因时应拆开 Raft 选举、Topo 发布、SDK 刷新、重试预算与尾延迟。面试官更看重你会不会解释测量口径，而不是记住最高 QPS。看 `docs/v0.1.0/benchmark/` 与 `docs/v0.1.0/retry.md`。

### K9. Q73/Q76：推荐架构如何从这个项目延伸？

先问清数据是什么：用户实时特征、模型配置、实验规则、候选召回索引的读写模型完全不同。AdvisKV 的 key 路由和副本复制可用于讨论特征或状态 KV，但当前内存 Map、固定分片和单进程控制面限制了容量与生产可用性。向量近邻搜索或离线训练不属于它的功能。

若给 10 万 QPS/p99 10 ms 的目标，应先拿读写比、key/value 大小、热 key、跨机拓扑、故障余量，再对单 shard、单节点、整链路逐层测量，最后估算机器并留安全余量。不能把单机报告数直接乘机器数。这里是系统设计推演，不应写成已交付推荐平台。

### K10. Q78/Q80：怎样把一致性经验迁移到 Agent？

Agent 调用外部工具时，超时可能发生在工具已执行、结果未返回之后，与 KV 写 UNKNOWN 的问题相似。给每个逻辑动作稳定的幂等键，把输入版本、执行状态和结果持久化；重试沿用同一键。若外部工具本身不支持幂等，必须有查询、补偿、审批等业务策略，不能由存储层许诺 exactly-once。

长任务还要保存阶段边界，worker 崩溃后先恢复已确认的步骤，再继续下一步；多个 worker 同时恢复同一任务时需所有权/租约与版本控制。可借鉴本项目 request ID 与 reconcile 思路，但当前仓库没有 Agent 框架接入、任务表或工具执行器。
