# AdvisKV 分层面试题库与评分标准

> 先读[项目速读](项目速读.md)和[证据与边界](证据与边界.md)。题库按项目主线、基础原理、故障排查、岗位设计题组织。每题的“合格”是至少应说出的事实，“加分”是能经受追问的因果与取舍，“失分”列出常见错误。代码入口用于复盘，不代表该场景在本次全部复测。标有“设计推演”的题目不属于当前已实现功能。

## 使用方法与统一评分

每题 0–4 分：**0** 没有回答或核心结论相反；**1** 只说术语，不能讲流程；**2** 说清“合格”要点；**3** 再说清“加分”中的一个边界、取舍或故障；**4** 能结合代码/测试定位并解释追问。含错误保证（例如把 `UNKNOWN` 说成一定没写入）时最高 1 分。系统设计题的 4 分还要有量化目标、演进和验证方案。先独立回答 90 秒，再看标准；项目题应能打开对应源码给面试官解释。

## A. 先讲清项目（1–8）

### 1. 用 30 秒介绍 AdvisKV

**合格**：C++17 分布式 KV；Catalog 管 DDL、Topo 管副本和路由、Storage 用 Raft/WAL/Snapshot，SDK 路由请求。**加分**：给出三副本本地 E2E 证据与单进程控制面、固定 shard 等边界。**追问**：一次 Put 经过哪些模块？**失分**：声称生产部署或 AI 功能已完成。**依据**：`README.md`、`scripts/verify_project.py`。

### 2. Catalog、Topo、Storage 为什么拆开？

**合格**：分别承担库表元数据/DDL、期望副本与路由、实际数据复制。**加分**：说明控制面异步收敛和数据面高频读写的节奏不同；Catalog/Topo 当前单进程是可用性短板。**追问**：Topo 故障时已有路由能否继续访问？需按 SDK 缓存和路由过期条件回答。**失分**：说三个模块都通过 Raft 高可用。**依据**：`src/catalog/`、`src/topo/`、`src/storage/`。

### 3. 一次建表何时算完成？

**合格**：Catalog 持久化 ADDING，Topo 建目标副本，Storage 执行创建，表与可写路由满足条件后进入就绪。**加分**：区分 DDL RPC 的 OK 与最终 NORMAL；Topo 不可达可由 reconciler 后续重试。**追问**：启动时没有足够健康节点怎么办？**失分**：把“请求返回 OK”当“已可读写”。**依据**：`src/catalog/service/ddl_service.cpp`、`src/topo/service/table_service.cpp`。

### 4. 一次 Put 的完整路径是什么？

**合格**：SDK 查路由 → Leader RPC → Replica 提议 Raft 日志 → 多数派提交 → apply 到状态机；日志由持久化层处理。**加分**：说明在路径中超时可能产生未知结果，同一逻辑请求沿用 `request_id`。**追问**：本地日志写入后但未多数派确认能否回 OK？**失分**：将 WAL 写入等同多数派提交。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica.cpp`、`src/storage/raft/core/`。

### 5. 一次 Get 为什么没有直接读 Map？

**合格**：确认自己仍是 Leader、取得 read index、apply 至该位置再读取。**加分**：解释新 Leader 当前任期 no-op 提交和多数派确认，指出多数派不可达时读可能失败。**追问**：如果允许陈旧读如何设计独立 API？**失分**：只看 `is_leader` 就声称线性一致。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

### 6. 当前项目最强的工程证据是什么？

**合格**：最小三副本 E2E 本机通过；仓库有单测、故障 E2E、benchmark 报告。**加分**：区分本次抽验与未重跑的测试，讲出可重复命令。**追问**：历史数字的机器和工作负载？**失分**：说 256 项本机全通过，或将历史 benchmark 说成今天新测。**依据**：`scripts/verify_project.py`、`docs/v0.1.0/benchmark/`。

### 7. 项目的最大限制是什么？

**合格**：内存 Map（容量受内存限制，恢复数据量大时较慢）；shard 数建表时固定（不能 split/rebalance）；Catalog/Topo 单进程（控制面无故障接管）；`request_id` 无 TTL（去重记录持续增长）。**加分**：按业务瓶颈排序：数据容量与恢复、热点扩容、控制面可用性、去重记录增长。**追问**：先改哪个、如何验收？例如接入磁盘 KV 引擎，测大数据集下的读写、重启恢复时间和峰值内存。**失分**：只说“还要优化性能”；认为 Snapshot 会降低 Map 内存占用，或增加副本数等于 shard 扩容。**依据**：`README.md`“当前限制”、`docs/版本.md`“后续”。

### 8. 如果面试官问你究竟做了什么？

**合格**：按个人真实工作选一条链路，讲背景、方案、取舍、问题、结果，并打开对应代码/测试。**可选讲法**：SDK 重试——路由错误时刷新路由；不确定写复用 `request_id` 重试，预算耗尽返回 `UNKNOWN`。Get——路由到 Leader，经 ReadIndex 多数派确认并 apply 到安全位置后读 Map。**加分**：明确个人与团队边界、哪些结果是历史报告。**追问**：最难的 bug 如何复现？**失分**：把整个仓库每项功能都说成个人独立完成，却无法解释。**依据**：[七个故事](证据与边界.md)、`src/sdk/client.cpp`、`src/storage/replica/replica_read_index_checker.cpp`。

**回答示例（按自己的实际贡献修改）**：

- **SDK 重试**：“我负责/参与/分析 SDK 的 Put 重试。SDK 先从路由缓存找 shard 的 Leader；遇到 `NOT_LEADER` 或 `RPC_ERROR` 等错误时会刷新路由并重试，遇到 `NOT_YET_COMMIT` 则可在预算内重试但不刷新路由。每次重试沿用同一个 `request_id`，并受总超时和重试次数限制；仍无法确认结果时返回 `UNKNOWN`，因为请求可能已经提交。可沿 `KVClient::put()` → `run_kv_request()` → `execute_with_retry()` 查看，再看状态机如何记录 request ID。”
- **Get 链路**：“我负责/参与/分析 Get 的线性一致读。SDK 按 key 算 shard，从路由中选 Leader；Storage 的 `Replica::get()` 不只检查本地 Leader 标记，而是调用 ReadIndex 检查当前任期提交状态，并向副本确认多数派仍认可自己。确认后取得 `read_index`，apply 已提交日志直到 `apply_index >= read_index`，再调用状态机的 `get()` 读 Map。多数派不可达或 ReadIndex 未就绪时返回错误，不冒险返回旧值。可沿 `KVClient::get()` → `Replica::get()` → `ReplicaReadIndexChecker` → `RaftCore::build_append_entries_for_read()` 查看。”

## B. C++、并发与工程基础（9–18）

### 9. SDK 路由快照如何避免读写竞争？

**合格**：建好新的不可变 `TableRouteSnapshot` 后，用 `shared_ptr` 原子发布；读线程通过原子 load 取得完整快照。**加分**：不会读到半更新路由，但快照仍可能过期，遇到 `NOT_LEADER` 等错误需刷新。**追问**：原子操作和引用计数的成本？**失分**：认为线程安全就代表路由最新。**依据**：`src/sdk/route_cache.cpp`。

### 10. Replica 为什么需要多个锁和任务队列？

**合格**：需要多把锁，因为 Raft Core、KV 状态机和 Snapshot/持久化是不同的共享状态，需分别保护；需要任务队列，因为 RPC、心跳和复制响应可能并发到达，Raft 状态变化要排队串行处理，写提案还可合批。**加分**：apply、RPC 等仍可并发；注意锁顺序，避免持锁等待网络。**追问**：如何排查死锁？**失分**：认为整个 Storage 是单线程，或“用了 mutex 就没有并发问题”。**依据**：`src/storage/replica/replica.h`、`src/storage/replica/replica_loop.cpp`、`src/common/serial_task_runner.cpp`。

### 11. `std::atomic` 与 mutex 如何选择？

**合格**：单个独立值（如计数器）用 `atomic`；多个字段需一起保持一致时用 `mutex`。**加分**：SDK 的 request ID 序号用 `fetch_add(relaxed)`；路由快照完整构造后原子发布；Raft Core 多字段由 mutex 保护。`relaxed` 保证计数原子递增，但不用于同步其他数据。**追问**：为什么不能把所有字段都改成 atomic？**失分**：认为 atomic 自动保证多个字段的一致性。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/storage/replica/replica_loop.cpp`。

### 12. C++ 对象生命周期在异步任务中有什么风险？

**合格**：后台任务/回调若持有对象指针，对象过早销毁会导致悬空访问；析构前要停止任务并等待线程退出（`stop`/`join`）。**加分**：`RouteCache` 析构时停止刷新任务；Replica 先停 apply 和消息线程，再停 loop。`shared_ptr` 不会自动取消任务或保证关闭顺序。**追问**：怎样避免回调访问已销毁对象？**失分**：认为用了 `shared_ptr` 就无需管理异步任务。**依据**：`src/sdk/route_cache.cpp`、`src/common/background_task.cpp`、`src/storage/replica/replica.cpp`。

### 13. 如何判断一个 Raft 并发 bug 可复现？

**合格**：固定节点和初始 Leader，控制分区及消息顺序；记录 term、日志/commit index、成员角色和消息时序。**加分**：模拟集群适合复现 Raft 状态问题；真实线程竞态用并发测试和 TSan 检查，ASan 补查内存错误。**追问**：如何稳定复现旧 Leader 收到延迟消息？**失分**：只靠随机 sleep 或把逐步 tick 的协议测试说成并发测试。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`scripts/asan/`。

### 14. `request_id` 的生成与碰撞风险？

**合格**：默认 `request_id` 由进程随机实例值和原子递增序号组成；同一次 SDK 写调用的重试复用该 ID。**加分**：跨重启重试需由调用方保存并传回原 ID；Storage 对相同 ID 去重，并拒绝内容不同的复用。随机 ID 的碰撞概率低但非零。**追问**：跨地域业务 ID 如何设计？**失分**：重试时生成新 ID。**依据**：`src/sdk/client.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/replica/replica_loop.cpp`。

### 15. 为什么要把 RPC 总超时和单次 RPC 超时分开？

**合格**：单次 RPC timeout 限制一次网络调用；总 timeout 限制完整 Put/Get（含路由刷新、重试和退避）。每次调用按 `min(剩余总预算, 单次 RPC 上限)` 设置 deadline。**加分**：同时限制重试次数；例如默认单次 RPC 1 秒、总请求 3 秒。**追问**：每次重试如何计算剩余时间？**失分**：每次重试都重新获得完整总超时。**依据**：`src/sdk/client.cpp`、`src/sdk/config.h`。

### 16. RAII 在本项目中解决什么？

**合格**：RAII 将清理绑定到对象析构，函数提前返回也会执行；项目 `Defer` 用于记录请求结果、关闭文件描述符。**加分**：引用捕获的变量必须活得比 guard 久，清理函数不应抛异常。**追问**：`Defer([&])` 何时安全？**失分**：把 RAII 仅理解为智能指针。**依据**：`src/common/defer.h`、`src/sdk/client.cpp`、`src/storage/persist/persist_engine.cpp`。

### 17. 如何避免哈希分片在进程间不一致？

**合格**：SDK 与 Topo 共用固定的 FNV-1a 64 位哈希，按 `hash(key) % shard_count` 算 shard。**加分**：改变 shard 数或哈希算法会重映射 key，需迁移数据；当前 shard 数建表时固定。**追问**：如何设计 split 迁移？**失分**：用不保证跨版本稳定的 `std::hash` 做持久路由，或直接改 shard 数。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`、`src/topo/service/route_service.cpp`。

### 18. 编译与运行依赖如何复现？

**合格**：`git submodule update --init --recursive` 获取 vcpkg，运行 `scripts/setup.sh` 安装依赖，`scripts/build.sh` 构建，再分别运行 C++ 测试和 `scripts/e2e_pytest.sh`。**加分**：同一 build 目录的 CMake generator 必须一致；可按依赖、配置/编译、测试运行阶段定位 CI 失败。**追问**：如何切换 Ninja 和 Makefiles？**失分**：在已有 build tree 中混用 generator，或只给本机绝对路径。**依据**：`CMakeLists.txt`、`scripts/setup.sh`、`scripts/build.sh`、`scripts/run_test.sh`、`scripts/e2e_pytest.sh`。

## C. RPC、SDK 与结果语义（19–28）

### 19. 路由缓存冷启动时怎么处理？

**合格**：冷启动缓存 miss 时，SDK 向 Topo 拉整表路由，缓存后按 key 算 shard 并选 Leader；拉取失败则返回错误，不盲发 Storage。**加分**：后台定期刷新与路由错误后的请求路径刷新并存；缓存命中时不必每次访问 Topo，但可能过期。**追问**：Topo 暂时不可用而缓存已有路由时怎么办？**失分**：认为每次请求都必须访问 Topo，或缓存永远最新。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/sdk/topo_route_client.cpp`。

### 20. 哪些错误触发刷新路由？

**合格**：可重试错误分两类：路由可能失效（`NOT_LEADER`、`REPLICA_NOT_FOUND`、`ROUTE_NOT_FOUND`、`IS_RECOVERING`、`RPC_ERROR`）则刷新路由；暂时未就绪（`NOT_YET_COMMIT`、`READ_INDEX_NOT_READY`、`RESOURCE_EXHAUSTED`）则沿原路由重试。**加分**：Storage 最多尝试 `max_retries + 1` 次，路由刷新次数受 `route_max_retries` 限制；路由查询、RPC 和退避共用总 deadline，每次 RPC 取单次上限与剩余时间的较小值。写重试复用同一 `request_id`。**追问**：为什么重试次数和总超时都要限制？**失分**：所有错误都刷新路由或无限重试。**依据**：`src/sdk/client.cpp`、`src/sdk/config.h`。

### 21. 写超时后 `UNKNOWN` 的含义？

**合格**：`UNKNOWN` 表示客户端在重试预算内无法确认写入是否提交；请求可能未到 Leader，也可能已提交但响应丢失。**加分**：用相同 `request_id` 和内容重试；单独 Get 只反映当前值，不能总证明原请求是否提交。**追问**：之后发生覆盖写，Get 为什么无法确认原请求？**失分**：把 `UNKNOWN` 当成确定失败。**依据**：`src/sdk/client.cpp` 中 `finalize_status`、`execute_with_retry`。

### 22. 幂等写如何落地？

**合格**：SDK 为每笔逻辑写入生成 `request_id`，重试时复用。Storage 先查已应用记录，再查 inflight 提案：同 ID、同内容则去重或等待；同 ID、不同内容则报错；都没有才提交新 Raft 提案。**加分**：请求记录保存在状态机并纳入 Snapshot，重启后仍可去重；当前无 TTL，长期运行会持续增长。**追问**：客户端重启后怎样复用原 ID？**失分**：重试时生成新 ID。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 23. RPC 返回 OK 就代表业务成功吗？

**合格**：区分 gRPC 传输状态与响应 `base_rsp` 业务状态；gRPC `OK` 只表示 RPC 通信完成，业务仍可能是 `NOT_LEADER`。**加分**：SDK 检查两层状态并据业务错误决定刷新路由/重试；RPC 超时未收到响应时，写结果可能未知。**追问**：超时但服务端已提交怎么办？**失分**：只检查 `grpc::Status::OK`。**依据**：`src/storage/handler/storage_service_impl.cpp`、`src/sdk/storage_client.cpp`。

### 24. 为什么重试可能放大负载？

**合格**：服务变慢导致超时，客户端重试会额外增加 Storage/Leader 和 Topo 压力，进而造成更多超时，形成负载放大。**加分**：项目已限制重试次数、路由刷新次数和总 deadline，并用指数退避；生产化可加 jitter、限流和熔断，观察重试率、成功率与尾延迟验收。**追问**：如何避免雪崩？**失分**：认为重试越多越可靠。**依据**：`src/sdk/client.cpp`；jitter、限流和熔断属于后续设计。

### 25. 读失败如何映射给调用方？

**合格**：`KEY_NOT_FOUND` 作为业务状态返回，不伪装成空值；`READ_INDEX_NOT_READY` 重试耗尽后映射为 `SDK_TRY_AGAIN`；路由错误按策略刷新并重试。**加分**：Get 不修改数据，不会有写入结果不确定的 `UNKNOWN`。**追问**：如果调用方需要弱一致读怎么办？**失分**：把所有读失败当成 key 不存在或空值。**依据**：`src/sdk/client.cpp`、`src/sdk/storage_client.cpp`、`src/storage/replica/replica.cpp`。

### 26. 如何给 SDK 定义可观察指标？

**合格**：看三类指标：请求结果（成功/失败/`UNKNOWN`）、重试与路由（逻辑请求数、Storage RPC 尝试、缓存命中/刷新）、延迟（端到端、路由、RPC 的 p95/p99）。**加分**：区分逻辑请求与重试 attempt；切主时测从故障到稳定成功的时间，并观察成功率、`UNKNOWN`、重试量和尾延迟。**追问**：如何量化切主窗口？**失分**：只看平均 QPS。**依据**：`src/sdk/client.cpp`、`src/sdk/route_cache.cpp`、`src/sdk/storage_client.cpp`、`docs/v0.1.0/retry.md`。

### 27. 如果客户端持有旧 table_id，会怎样？

**合格**：同名表删除后重建会分配新 `table_id`；旧缓存路由仍指向旧副本，遇副本/路由错误后 SDK 刷新并获取新路由，新表不会继承旧数据。**加分**：E2E 验证删表重建后旧 key 不可见。**追问**：如何用表代际版本防 ABA？**失分**：仅凭同名就认为是同一张表。**依据**：`src/catalog/store/catalog_store.cpp`、`src/sdk/route_cache.cpp`、`test/e2e/test_basic_chain.py`。

### 28. 什么场景下客户端不该自动重试？

**合格**：参数错误、确定的业务错误不应重试；暂时性错误也受重试次数和总超时限制。写结果耗尽预算仍无法确认时返回 `UNKNOWN`。**加分**：邮件/支付等外部副作用需业务幂等键；本项目 Delete 不存在的 key 仍返回 `OK`（确保 key 不存在）。**追问**：Delete 不存在键的业务语义是什么？**失分**：所有失败都无限重试，或把 `UNKNOWN` 当成确定失败。**依据**：`src/sdk/client.cpp`、`src/storage/engine/map_engine.cpp`；外部副作用为设计推演。

## D. 分片、Topo 与副本控制（29–38）

### 29. key 如何定位到 shard？

**合格**：SDK 用固定哈希计算 `hash(key) % shard_count` 得到 shard，再查该 shard 路由；Topo 使用同一算法。`table_id` 标识表/路由，不参与 key 哈希。**加分**：shard 数建表时固定，改变后需迁移数据；多 shard 不能自动分散单个热点 key。**追问**：如何应对热点 key？**失分**：认为 table_id 参与哈希，或多 shard 会自动均衡热点。**依据**：`src/common/stable_hash.h`、`src/sdk/route_cache.cpp`、`src/topo/service/route_service.cpp`。

### 30. Topo 为什么只发布一个可写 Leader？

**合格**：每个 shard 的写入由一个 Leader 统一排序；Topo 只发布恰有一个有效 Leader 的路由。**加分**：无 Leader 或最高 term 冲突时清除路由；不同 term 冲突时保留最高 term。切主期间可能暂时不可写，以避免发布不安全路由；Storage/Raft 仍会校验 Leader 身份。**追问**：多个不同 term Leader 上报怎么办？**失分**：随机选一个。**依据**：`src/topo/service/route_service.cpp`、`test/topo/service/route_reconcile_service_test.cpp`。

### 31. 节点心跳承担什么职责？

**合格**：NodeAgent 定期向 Topo 上报节点及本地副本状态；Topo 更新健康/路由视图并返回副本管理指令。**加分**：心跳丢失不等于节点永久损坏；这与 Raft 副本间用于选主/复制的心跳不同，也不能证明写入已提交。**追问**：网络分区时双方视图为何不同？**失分**：把 Topo 心跳当作 Raft 心跳或提交确认。**依据**：`src/storage/node_agent/node_agent.cpp`、`src/topo/service/node_service.cpp`、`src/topo/service/replica_group_service.cpp`。

### 32. 期望状态和实际状态为什么分开？

**合格**：desired 记录目标副本数/位置；observed 记录 Storage 心跳上报的副本状态和 Raft 成员角色。Reconciler 比较两者并多轮推进，例如目标 3 副本时，必须等 3 个副本 READY 且成为 voter 才算就绪。**加分**：异步操作可重试，控制面重启后能继续收敛。**追问**：目标与实际长期不一致时如何报警？**失分**：下发创建指令就当副本已就绪。**依据**：`src/topo/model/model.h`、`src/topo/reconcile/`、`src/topo/service/table_service.cpp`。

### 33. 在线扩容副本一般为什么先加 learner？

**合格**：新副本先以 Learner 加入，接收日志/快照但不参与投票和多数派；追到 Leader 当前日志位置后再提升为 Voter。**加分**：未追平就计入多数派可能影响提交与可用性。**追问**：快照传输期间日志继续增长怎么办？**失分**：副本一创建就当作健康 Voter。**依据**：`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_replication.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 34. 缩容到零意味着什么？

**合格**：缩容到 0 后无 KV 路由，读写返回 `ROUTE_NOT_FOUND`；Storage 删除副本及其持久化数据，扩容会创建新副本，不能假设旧数据保留。**加分**：保留数据需先备份；现有 E2E 验证 0 副本不可读写和扩回后可写，但未验证旧数据保留。**追问**：如何安全地缩到 0 并保留数据？**失分**：说零副本仍可读，或扩回后数据必然恢复。**依据**：`tools/e2e/cases/scale_to_zero_case.h`、`src/storage/replica/replica_manager.cpp`、`src/topo/service/table_service.cpp`。

### 35. 副本选择如何避免同故障域？

**合格**：只选目标资源池内在线且地址有效的节点；同 shard 不重复选节点，并优先分散 DC，再平衡节点副本数。**加分**：候选节点或 DC 不足会限制隔离效果；DC 标签须与真实部署一致，同机多进程不等于跨故障域容灾。**追问**：可用 DC 数不足怎么办？**失分**：仅凭不同 DC 标签就声称实现物理故障隔离。**依据**：`src/topo/selector/node_selector/node_selector.cpp`、相应测试。

### 36. 新 Leader 出现后路由多久更新？

**合格**：切主后需经过 Raft 选举、NodeAgent 心跳上报、Topo 重建路由、SDK 刷新并重试；旧 Leader 可能先返回 `NOT_LEADER`。**加分**：Topo/SDK 后台任务的周期只是检查间隔，不是恢复时间保证；按故障发生到业务稳定成功测恢复窗口。**追问**：如何测切主期间的成功率和恢复时间？**失分**：把 Raft 选举时间当作业务恢复时间。**依据**：`src/topo/background/background.cpp`、`src/topo/main/main.cpp`、`src/sdk/route_cache.cpp`、`scripts/failover_bench.sh`。

### 37. 控制面故障会影响哪些操作？

**合格**：Catalog 故障影响 DDL/元数据；Topo 故障影响取路由、路由刷新和拓扑调度。已有有效路由时 KV 可能暂时继续访问 Storage；路由失效或冷启动时则可能失败。**加分**：数据面能否写还取决于 Storage Raft 多数派；缓存不能替代控制面高可用。**追问**：如何给 Catalog/Topo 做高可用？**失分**：称控制面故障对业务完全无影响，或 Storage 数据立即丢失。**依据**：`src/sdk/route_cache.cpp`、`src/catalog/main/main.cpp`、`src/topo/main/main.cpp`、`README.md`。

### 38. 如何设计在线 shard split？【设计推演】

**合格**：当前不支持在线 split；设计上需版本化路由，复制旧 shard 数据并追平迁移期间的写入，再切换路由；旧路由请求应刷新/重试，并保留回滚方案。**加分**：定义迁移期间一致性、限速和完成证据。**追问**：如何避免复制期间的写入丢失？**失分**：直接改 `shard_count` 并重新取模。**依据**：`README.md` 当前限制、`src/sdk/route_cache.cpp`。

## E. Raft、一致性与成员变更（39–52）

### 39. Raft 选主保证了什么？

**合格**：候选者先经 PreVote，再在新 term 请求投票；日志足够新的候选者获当前 voter 多数票后成为 Leader。**加分**：选举不等于写入提交，每笔写仍需多数派确认；少数派旧 Leader不能提交，看到更高 term 后退位。**追问**：3 个 voter 中少数派能否选出可提交的 Leader？**失分**：认为任意节点可单独继续写，或 Leader 当选即代表数据已复制。**依据**：`src/storage/raft/core/raft_core_election.cpp`、`src/storage/raft/raft_membership.cpp`、`test/storage/raft/core/raft_cluster_test.cpp`。

### 40. term、log index、commit index、apply index 分别是什么？

**合格**：`term` 是选举任期，`index` 是日志位置；`commit_index` 是 Raft 已提交到的位置，`apply_index` 是状态机已执行到的位置。顺序为追加日志→多数派确认→commit→apply。**加分**：通常 `apply_index ≤ commit_index ≤ last_log_index`；重启从 `raft_meta`、WAL 和 Snapshot 恢复。**追问**：日志已写入 WAL 就一定提交了吗？**失分**：混淆追加、提交和 apply。**依据**：`src/storage/raft/`、`src/storage/replica/replica_applier.cpp`、`src/storage/persist/persist_engine.cpp`。

### 41. 为什么旧任期日志不能只凭多数派复制直接提交？

**合格**：旧任期日志即使复制到多数副本也不能直接宣布提交；Leader 需先让当前任期日志获多数派确认，之前的日志前缀才随之安全提交。**加分**：新 Leader 追加 no-op 建立当前任期的提交位置，ReadIndex 也依赖此条件。**追问**：当前任期 no-op 有什么作用？**失分**：认为多数副本有日志就一定已提交。**依据**：`test/storage/raft/core/raft_cluster_test.cpp` 的 Figure8 用例、`src/storage/raft/raft_replication.cpp`、`src/storage/raft/core/raft_core_election.cpp`。

### 42. PreVote 解决什么，又不解决什么？

**合格**：PreVote 是正式选举前的探测；获得多数派预投票后才提升 term 并开始正式选举，减少隔离旧节点抬高 term 干扰活跃 Leader。**加分**：之后仍需日志足够新并获多数派正式选票；PreVote 不选出 Leader，也不解决控制面单点。**追问**：PreVote 接收者会因预投票请求提升 term 吗？**失分**：把 PreVote 当成正式选票或 Leader 身份。**依据**：`src/storage/raft/core/raft_core_election.cpp`、PreVote 用例。

### 43. 日志冲突如何修复？

**合格**：Follower 用 `prev_log_index/term` 校验日志前缀；不匹配则拒绝，Leader 回退 `next_index` 重试。发现冲突时截掉并替换未提交后缀；日志已压进 Snapshot 时先安装 Snapshot，再复制后续日志。**加分**：已提交前缀不可被覆盖。**追问**：Follower 落后到 Leader 已压缩的日志之前怎么办？**失分**：不校验前缀、直接追加到尾部。**依据**：`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_log.cpp`、`src/storage/raft/raft_peer_progress.cpp`。

### 44. 多数派提交为什么是 N/2+1？

**合格**：quorum=`floor(N/2)+1`，任意两个多数派有交集；3 个 voter 需 2 票、可容忍 1 个故障。**加分**：例如写入由 `{A,C}` 确认提交，A 故障后新选举多数派 `{B,C}` 与其交于 C；C 的日志新旧检查可阻止缺少已提交日志的 B 当选。4 个 voter 需 3 票、仍只容忍 1 个故障；5 个需 3 票、可容忍 2 个。Learner 不计入 quorum，跨 DC 确认会影响写延迟。**追问**：为什么 3 增至 4 未提升容错？**失分**：把 Learner 计入多数派。**依据**：`src/storage/raft/raft_membership.cpp`、Raft 集群测试。

### 45. Leader 崩溃时为什么可能返回 UNKNOWN？

**合格**：Leader 崩溃时，请求可能已经被多数派提交，只是响应没到客户端；也可能只存在于 Leader 本地，尚未提交，之后会被新 Leader 覆盖。客户端超时无法区分这两种情况，所以在重试预算耗尽后返回 `UNKNOWN`。**加分**：重试同一笔写入要复用 `request_id`，不能把超时当成确定失败。**追问**：为什么简单 Get 不能严格判定原请求？**失分**：把超时当成确定失败。**依据**：`src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`、`docs/v0.1.0/retry.md`。

### 46. 项目 Get 的线性一致读前提有哪些？

**合格**：Get 确认本节点是 Leader、当前任期已有已提交日志，并获多数派确认；取 `read_index = commit_index`，apply 到 `apply_index ≥ read_index` 后再读 Map。**加分**：多数派不可达或 ReadIndex 未就绪时失败/稍后重试，不返回可能过期数据。**追问**：单副本时如何满足多数派？**失分**：只看本地 Leader 标记就读 Map。**依据**：`src/storage/raft/core/raft_core_read.cpp`、`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/replica/replica.cpp`。

### 47. ReadIndex 与 Lease Read 有什么差别？【原理与推演】

**合格**：ReadIndex 每次读都确认多数派；Lease Read 在多数派确认形成的租约有效期内可本地读，延迟较低。**加分**：Lease Read 的安全性依赖时钟/暂停假设；本项目实现 ReadIndex，未实现 Lease Read。**追问**：进程暂停或时钟误差如何影响租约安全？**失分**：把 ReadIndex 说成纯本地读，或声称项目已有 Lease Read。**依据**：`src/storage/replica/replica_read_index_checker.cpp`、`src/storage/raft/core/raft_core_read.cpp`。

### 48. 成员变更时 quorum 怎么看？

**合格**：Quorum 按当前 Voter 集合计算，Learner 不投票、不计数；新副本追平后升为 Voter，配置变更经 Raft 日志生效。**加分**：3→4 个 Voter 后 quorum 从 2 变 3；3 缩到 2 后仍需 2 票，失去容忍 1 个故障的能力。成员变更需序列化、不能跳过 Learner 追赶。**追问**：3 voter 缩到 2 voter 时可容忍几个故障？**失分**：把 Learner 计入 quorum，或只改 Topo 目标就认为成员配置已变。**依据**：`src/storage/raft/raft_membership.cpp`、`src/storage/raft/core/raft_core_append.cpp`、成员变更测试。

### 49. 分区后旧 Leader 恢复，如何避免它覆盖新历史？

**合格**：3 副本中 A 分区、B/C 选出更高 term 的新 Leader；A 恢复后见高 term 退位，新 Leader 按日志匹配修复 A 的未提交冲突后缀，已提交日志必须保留。**加分**：少数派旧 Leader不能提交；SDK 遇旧路由的 `NOT_LEADER` 会刷新路由，超时写可能返回 `UNKNOWN` 并须复用 request_id。**追问**：A 分区期间已成功返回的写能丢吗？**失分**：认为节点恢复时本地日志优先。**依据**：`src/storage/raft/core/raft_core_election.cpp`、`src/storage/raft/core/raft_core_append.cpp`、`src/storage/raft/raft_log.cpp`、`src/sdk/client.cpp`。

### 50. 同一 shard 出现两个 Leader 上报怎么办？

**合格**：双 Leader 上报可能是心跳延迟造成的观测冲突；Topo 对不同 term 保留最高者，最高 term 相同则清除可写路由。**加分**：路由不是写入许可，Storage/Raft 多数派才决定能否提交；SDK 遇 `NOT_LEADER` 刷新路由。已确认提交的写不能丢，超时未确认则为 `UNKNOWN`，用原 `request_id` 重试。**追问**：如何区分上报冲突与 Raft 安全性被破坏？**失分**：Topo 随机选 Leader，或把超时当确定失败。**依据**：`src/topo/service/route_service.cpp`、`src/storage/raft/raft_replication.cpp`、`src/sdk/client.cpp`、RouteServiceReconcile 测试。

### 51. Raft 正确性如何测试？

**合格**：协议测试覆盖选主、复制、少数派、崩溃切主、冲突修复、追赶和 Snapshot。**加分**：区分逐步 tick 模拟、并发提议测试、多进程 E2E 和 Maelstrom 故障注入；它们覆盖不同层次，不能互相替代。**追问**：如何验证线性一致历史？**失分**：只测 Put 后立即 Get，或把协议模拟说成真实并发测试。**依据**：`test/storage/raft/core/raft_cluster_test.cpp`、`test/e2e/`、`tools/maelstrom_raft/`。

### 52. 为什么 Raft 不自动解决所有数据一致性问题？

**合格**：Raft 保证单个 Raft 组的日志顺序与提交；业务仍需处理请求去重、确定性状态机和一致读。不同 shard 是独立 Raft 组，不自动组成事务。**加分**：跨 shard 转账可能一边扣款已提交、另一边入账未提交；本项目无跨 shard 事务和在线 split。**追问**：如何设计两个 shard 的原子更新？**失分**：认为 Raft 自动提供全局事务。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/sdk/client.cpp`、`README.md`。

## F. WAL、Snapshot 与恢复（53–62）

### 53. WAL 为什么要在应用状态机前持久化？

**合格**：重启后可以依据日志重建尚未进入 Snapshot 的状态，Raft 承诺不能只存在内存。**加分**：区分本地持久化、复制多数派和状态机 apply 三个完成点。**追问**：fsync 失败应怎么办？**失分**：只要写入 page cache 就等于所有故障模型下持久。**依据**：`src/storage/persist/persist_engine.cpp`、`src/storage/replica/replica_applier.cpp`。

### 54. Snapshot 里要放哪些内容？

**合格**：KV、状态机 apply index/term、请求去重记录，以及恢复 Raft 成员所需元数据。**加分**：说明缺少 request record 会使重启后的重复写可能再次执行。**追问**：Snapshot 与 WAL 裁剪顺序如何保证安全？**失分**：只把 Map 键值序列化。**依据**：`src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp`。

### 55. 为什么需要 WAL 截断与快照边界？

**合格**：Snapshot 覆盖以前的日志，保留后续日志便于恢复与追赶；边界不连续会产生缺口。**加分**：崩溃发生在写 Snapshot、替换文件、裁剪 WAL 的不同阶段，恢复需验证完整性。**追问**：先删 WAL 再写 Snapshot 会怎样？**失分**：只按文件大小轮转不看 index。**依据**：`src/storage/persist/persist_engine.cpp`、PersistEngine 测试。

### 56. WAL 尾部损坏如何区分处理？

**合格**：读取记录长度/CRC，未提交损坏尾部可截断；已提交部分损坏需谨慎，可能进入追赶恢复。**加分**：解释为何不能静默丢掉已提交数据。**追问**：如果多数派都损坏该怎么办？应说明当前方案边界。**失分**：遇到 CRC 错误直接清空全部数据。**依据**：`src/storage/persist/persist_engine.cpp`、`test/storage/persist/wal_crash_injection_test.cpp`。

### 57. 落后副本何时走日志追赶，何时走 Snapshot？

**合格**：Leader 仍持有目标日志时发 AppendEntries；所需日志已被压缩时安装 Snapshot，再补后续日志。**加分**：考虑安装过程中 Leader 继续写入，目标副本需追赶到最新提交位置后才能安全升 voter。**追问**：Snapshot 分片接收中断怎样续传或重试？**失分**：快照安装完成就直接假定最新。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`test/e2e/test_basic_chain.py`。

### 58. 为什么说当前是“内存引擎但支持持久化”？

**合格**：运行时读写由 Map 完成，WAL/Snapshot 保存可恢复状态；重启要加载到内存。**加分**：解释这与 RocksDB/LSM 的点查、压缩、写放大和容量模型不同。**追问**：数据超过内存怎么办？**失分**：称 Map 完全不落盘，或称已实现磁盘 KV 引擎。**依据**：`src/storage/engine/map_engine.cpp`、`src/storage/persist/persist_engine.cpp`。

### 59. Snapshot 生成时并发写如何保证一致视图？

**合格**：必须在确定的 apply index 捕获 KV 与去重记录的同一逻辑状态，并正确协调锁与持久化顺序。**加分**：定位 ReplicaSnapshotCoordinator 和 KvStateMachine 的捕获路径，说明长时间持锁的尾延迟风险。**追问**：怎样改为增量快照？**失分**：边遍历 Map 边无锁写文件却声称一致。**依据**：`src/storage/replica/replica_snapshot_coordinator.cpp`、`src/storage/raft/state_machine/kv_state_machine.cpp`。

### 60. 为什么恢复期间拒绝读写？

**合格**：本地状态可能落后于应有的提交位置，不应给客户端错误的成功读写；返回 IS_RECOVERING。**加分**：说明恢复完成判据与路由摘除需要协同。**追问**：如果只有一个健康副本怎样处理可用性？**失分**：Map 加载完成就立即对外宣称最新。**依据**：`src/storage/replica/replica.cpp`、`src/storage/raft/core/raft_core_recovery.cpp`。

### 61. 如何验证重启恢复？

## I. 故障排查题（85–94）

## J. 模拟面试顺序与复盘标准

**15 分钟快问**：1 → 4 → 5 → 7 → 21 → 40 → 53 → 65。目标是每题 90 秒内先给结论、再给一条代码证据；总分至少 24/32，且 21 与 40 不得低于 2 分。

**45 分钟项目深挖**：2 → 3 → 29 → 30 → 42 → 46 → 54 → 69 → 85 → 89。目标是能画出控制面/数据面、解释两处故障分支与一项当前限制；总分至少 30/40。

**60 分钟推荐架构/AI 场景**：73 → 74 → 75 → 76 → 78 → 80 → 81 → 84，最后由面试官任选 2 道故障题。每道设计题先问清 QPS、p99、数据量、一致性、故障域和预算，再给方案、取舍、演进与验收。不能把推演说成已实现。

每次复盘只记三列：**没讲出的关键事实、讲错的保证、无法定位的代码/测试**。优先修正“讲错的保证”；熟记术语但无法解释故障路径时，回到[项目速读](项目速读.md)重走一次请求链路。

以下答案是口述范例。面试时先给结论，再按面试官兴趣展开，不要一次背完。

### K1. Q4：一次 Put 究竟什么时候成功？

可以从客户端往下画五步。第一步，SDK 根据表路由快照和稳定哈希找到 shard 的 Leader。第二步，Storage RPC handler 根据 replica ID 找到 Replica。第三步，Replica 把带 `request_id` 的写交给 Raft 提议；持久化层在日志写入路径处理 WAL。第四步，Leader 收到有效多数派响应后推进 commit index，Replica 将已提交日志 apply 到 Map 状态机并记录 request ID。第五步，调用方得到明确 OK，才把这次逻辑写当作成功。

重点是四个位置不能混同：**请求发出、本地 WAL 写入、多数派提交、状态机应用**。本地写入只能证明这个节点接收了日志；少数派下写可能长期未提交并被后续 Leader 覆盖。超时还可能发生在服务端已提交但响应未送达之后，因此 SDK 返回 UNKNOWN 而不是“没写入”。复盘代码：`src/sdk/client.cpp` → `src/storage/handler/storage_service_impl.cpp` → `src/storage/replica/replica.cpp` → `src/storage/raft/core/`。

### K2. Q5/Q46：为什么读取要确认当前任期和多数派？

只检查本地 `is_leader` 不够：网络分区里的旧 Leader 可能尚未得知新 term。项目在构建读请求时要求当前任期已有已提交 entry，然后发送复制/心跳消息确认多数派对该 Leader 的认知，取得 read index；Replica 在状态机 apply 到该位置后才读 Map。这样多数派不可达时宁可返回错误，也不把旧值伪装成线性一致读。

追问时要解释“当前任期 entry”：新 Leader 刚当选时，对前任期日志的提交认知可能不完整；提交一条本任期 no-op 后，前面的安全前缀也能推进。项目的实现见 `src/storage/raft/core/raft_core_read.cpp` 与 `src/storage/replica/replica_read_index_checker.cpp`。这里讨论的是项目的 Leader 读路径，不包括未实现的 follower 陈旧读 API。

### K3. Q21：UNKNOWN 后业务应该怎么做？

先准确翻译：UNKNOWN 是**本次逻辑写是否提交无法确认**。例如 Leader 已提交，回包丢失；或者只有本地日志，随后被新 Leader 覆盖。客户端必须保留原请求的 `request_id` 和 payload，预算允许时用同 ID 重试；服务端查询已提交 request record 和在途记录，识别相同写或冲突写。如果最终仍无法确认，上层根据业务采取查询、补偿或人工处理。

不能把一次普通 Get 当成普遍的“提交证明”：相同 value 可能由另一写产生，原值也可能被后续写覆盖。更不能换一个 ID 直接重试非幂等副作用。对应 `src/sdk/client.cpp`、`src/storage/replica/replica_loop.cpp`。

### K4. Q32：为什么副本调整用 reconcile？

建表或改副本数横跨 Catalog、Topo、多个 Storage 和 Raft 成员变更。任何 RPC、进程或网络都可能在中间失败，单个同步请求无法安全等到全部动作完成。系统先持久化“想要什么”，后台反复观察“现在是什么”，一次只推进可安全执行的下一步。上层通过表状态看进度，Topo 依据节点与副本状态决定下一轮动作。

这要求操作幂等、状态转换可恢复、失败原因可观察；代价是 DDL 返回与数据就绪之间有时间差。要对面试官强调：`create_table` 返回 OK 代表 DDL 已被接纳，不代表所有副本已完成、路由已可写。阅读 `src/catalog/service/ddl_service.cpp`、`src/catalog/background/table_reconciler.cpp`、`src/topo/reconcile/`。

### K5. Q40/Q41：日志“复制了”为什么还可能不安全？

Raft 的 `log index` 表示位置；`commit index` 表示可安全认定的已提交前缀；`apply index` 表示状态机已执行到哪里。新 Leader 可能携带前任期日志，不能仅凭自己观察到旧日志在多数派存在就直接推进提交，因为成员与选举交错会出现 Figure 8 类反例。提交当前任期条目后，才可以安全推进相关前缀。

所以回答“写成功”不能只说“Follower 收到了”；还要问当前 term、voter 配置、多数派以及 apply。仓库有 Figure8 用例：`test/storage/raft/core/raft_cluster_test.cpp`，读前条件在 `src/storage/raft/core/raft_core_read.cpp`。

### K6. Q42：PreVote 的价值与代价

旧 Leader 与多数派隔离后可能不断发起新选举、提高 term；恢复连接时高 term 会迫使健康 Leader 退位，造成业务抖动。PreVote 在真正增加 term 前先征询“如果选举，我能否获多数派支持”，并考虑日志新旧和近期 Leader 活跃状态。多数派不同意时，隔离节点不应凭自己超时就扰乱健康集群。

它多一次消息往返，可能增加真正无 Leader 时的选举时间；它也不替代正式投票与日志安全检查。面试官若问效果，不要承诺零切主时间：项目有相关 Raft 用例，故障实验仍观察到业务失败/UNKNOWN。看 `src/storage/raft/core/raft_core_election.cpp` 与 `docs/v0.1.0/retry.md`。

### K7. Q54/Q56：为什么 Snapshot 不能只存 Map？

Map 只是业务值。要正确恢复，还需要知道这些值对应哪个 apply index/term、当时的成员信息及已处理的 request ID。否则重启后虽然读到旧值，却可能再次执行已经提交过的逻辑写。生成 Snapshot 时这些部分要来自同一应用边界；落盘后再安全处理被它覆盖的 WAL 前缀。

恢复时也不能见到损坏就随意丢数据。未提交的部分尾记录与已提交日志损坏有不同风险：前者可按恢复规则截断；后者需要标记并向其他副本追赶或暴露故障。看 `src/storage/raft/state_machine/kv_state_machine.cpp`、`src/storage/persist/persist_engine.cpp` 以及 WAL 崩溃注入测试。

### K8. Q65/Q69：怎么讲性能和故障数字才可信？

先把环境说全：v0.1.0 报告是在 M3 Pro 上以单机多进程测量，默认 16 线程、2 shard、3 replica、128 字节 value、30,000 请求。Put 约 9,800 success QPS 是该负载下的历史结果；本次本机没有重跑 benchmark。它可以证明测试方法和当时表现，不能预测跨机网络、不同键分布或生产容量。

故障结果也要给分母和时间窗口。历史报告在特定写负载下，增加重试次数降低了业务可见失败/UNKNOWN，但没有达到零失败。分析原因时应拆开 Raft 选举、Topo 发布、SDK 刷新、重试预算与尾延迟。面试官更看重你会不会解释测量口径，而不是记住最高 QPS。看 `docs/v0.1.0/benchmark/` 与 `docs/v0.1.0/retry.md`。

### K9. Q73/Q76：推荐架构如何从这个项目延伸？

先问清数据是什么：用户实时特征、模型配置、实验规则、候选召回索引的读写模型完全不同。AdvisKV 的 key 路由和副本复制可用于讨论特征或状态 KV，但当前内存 Map、固定分片和单进程控制面限制了容量与生产可用性。向量近邻搜索或离线训练不属于它的功能。

若给 10 万 QPS/p99 10 ms 的目标，应先拿读写比、key/value 大小、热 key、跨机拓扑、故障余量，再对单 shard、单节点、整链路逐层测量，最后估算机器并留安全余量。不能把单机报告数直接乘机器数。这里是系统设计推演，不应写成已交付推荐平台。

### K10. Q78/Q80：怎样把一致性经验迁移到 Agent？

Agent 调用外部工具时，超时可能发生在工具已执行、结果未返回之后，与 KV 写 UNKNOWN 的问题相似。给每个逻辑动作稳定的幂等键，把输入版本、执行状态和结果持久化；重试沿用同一键。若外部工具本身不支持幂等，必须有查询、补偿、审批等业务策略，不能由存储层许诺 exactly-once。

长任务还要保存阶段边界，worker 崩溃后先恢复已确认的步骤，再继续下一步；多个 worker 同时恢复同一任务时需所有权/租约与版本控制。可借鉴本项目 request ID 与 reconcile 思路，但当前仓库没有 Agent 框架接入、任务表或工具执行器。
